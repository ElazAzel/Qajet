# QAJET

Внешний отдел закупок для HR- и маркетинг-команд в Алматы: мерч, корпоративные
наборы, полиграфия. QAJET сравнивает не отдельные строки прайса, а целые
исполнимые варианты решения закупочной задачи, ведёт заказ до приёмки и
закрывающих документов.

Полная спецификация продукта — [`agents.md`](./agents.md). Она источник истины
для этого репозитория: любое изменение логики заказов, оплат, ролей или
поставщиков сверяется с ней в первую очередь. Правки в неё вносятся вместе с
кодом, а не постфактум.

## Честный статус

Проект в разработке; web production уже развёрнут на Vercel. Ниже — что
реально работает сейчас, без округления в большую сторону:

- Production: [qajet-seven.vercel.app](https://qajet-seven.vercel.app/).
  Текущий `main` автоматически собирается и публикуется Vercel; production
  smoke проверяет публичную главную, StartupBattle и fail-closed RFQ-ссылку.

- Каркас монорепо, дизайн-токены, четыре оболочки ролей (покупатель,
  консьерж, поставщик, админ) — экраны наполнены реальными данными, не
  заглушками.
- `packages/engine` — движок расчётов целиком (estimate, match, combine,
  leadtime, tax, learn), чистый TS с юнит-тестами.
- Схема Drizzle, RLS-политики, Supabase Auth, сид (15 поставщиков, 24
  закрытых заказа за 9 месяцев).
- Весь жизненный цикл заказа реально пишет в БД, от текстовой заявки до
  закрытия — не только продолжение уже существующего заказа. Покупатель
  создаёт заявку (`/buyer/requests/new`, выбор позиций из каталога —
  ниже честно про упрощение), концьерж берёт её в работу, считает оценку
  на реальной истории цен, подтверждает предоплату и рассылает RFQ
  подходящим поставщикам по категории и техпроцессам. Поставщик отвечает
  через свой дашборд (цена/срок/setup fee по позициям), концьерж
  предлагает план на живом `combine()`, покупатель утверждает, концьерж
  проводит операционные стадии (оплата поставщиков → производство →
  отгрузка), поставщик подтверждает доставку, покупатель принимает и
  закрывает со сверкой (возврат/доплата/точно). Единственный путь записи —
  `transition()` из `packages/engine/order` плюс RLS; аудит перехода пишет
  PostgreSQL-триггер в той же транзакции — см.
  [ADR-0006](./docs/decisions/0006-order-transition-write-path.md).
  Сценарий покрыт Playwright от чистой заявки до `closed`; live-прогон
  требует Supabase secrets, а публичный smoke запускается без них.
- Полная проверка этого цикла (сентябрь 2026) нашла и закрыла два реальных
  дефекта RLS, оба введены в этой же сессии при добавлении write-политик
  для интейка: бесконечную рекурсию политик `requests`↔`rfqs` (валила
  чтение `companies` на каждом заходе после логина) и утечку изоляции
  поставщиков — политики `rfqs_select_buyer_of_request`/
  `quotes_select_buyer_of_request`/`quote_lines_select_buyer_of_request`
  полагались на видимость `requests`, которая расширилась до поставщика
  вместе с новой политикой, и в результате поставщик A видел RFQ и КП
  поставщика B по тому же заказу. Обе категории — обязательный тест §15
  на изоляцию поставщиков; local run без `DATABASE_URL` пропускает DB-тесты,
  а обязательный real-Postgres прогон теперь прошёл в GitHub Actions
  (`rls-isolation`, 23 теста).
- PWA: офлайн-оболочка, манифест, установка на десктоп и телефон.
- Десктопная оболочка `apps/desktop` (Tauri 2 — меню, трей, глобальный
  хоткей, deep link, `.deb`/`.rpm`/`.AppImage`) и webview-скелет
  `apps/mobile` сохранены как отдельные проекты. Нативные iOS/Android
  проекты в этот финиш намеренно не входят.
- Playwright e2e (`apps/web/e2e`): сквозной сценарий заявка→закрытие в
  двух вариантах (возврат/доплата) и бюджет анимаций (без jank) на
  экране сравнения — оба против живой Supabase-сессии, самоотключаются
  без неё.
- Переносимость (фаза 8): `docker-compose.yml` + `apps/web/Dockerfile` —
  Next standalone + Postgres 17 + MinIO, поднято и проверено живьём;
  пошаговый [runbook переезда](./docs/runbook-migration.md) фиксирует,
  что перенесено, а что осталось организационным вопросом.
- RAG-инструмент разработки (`tools/rag`) — поиск по спецификации, ADR и
  журналу, доступный как MCP-сервер прямо в сессии.

Актуальный чек-лист фаз — [`docs/state/ledger.md`](./docs/state/ledger.md)
(генерируется автоматически, не редактируется руками; отмечает фазу
готовой по факту существования файлов, а не по полноте функциональности
внутри неё — это разошлось однажды именно с фазами 4–5, см. ADR-0006).

## Быстрый старт

```bash
pnpm install
pnpm dev            # apps/web на localhost:3000
```

```bash
pnpm lint           # Biome
pnpm typecheck      # tsc по всем пакетам монорепо (Turborepo)
pnpm test           # Vitest
pnpm --filter @qajet/web build   # production-сборка Next.js
```

```bash
pnpm rag:sync              # перегенерировать docs/state/ и переиндексировать корпус
pnpm rag:search <запрос>   # поиск по agents.md, ADR, журналу
pnpm rag:check             # индекс не отстал от кода (используется в CI)
pnpm rag:log <текст>       # запись в журнал сессии
```

## Структура репозитория

```
apps/
  web/          Next.js 16 — единственное приложение
packages/
  ui/           дизайн-система: токены, моушн-система, оболочки ролей
  engine/       (фаза 2) детерминированные алгоритмы, ноль внешних вызовов
  db/           (фаза 1) Drizzle: схема, RLS-политики, миграции, сид
  pd/           единственная точка доступа к персональным данным + maskPII()
tools/
  rag/          корпус знаний + индекс + MCP-сервер
docs/
  decisions/    ADR — инженерные решения с обоснованием
  journal/      журнал сессий разработки
  state/        генерируется `pnpm rag:sync`, не редактируется руками
```

## Известные ограничения

- **Персональные данные.** Supabase-проект MVP размещён в `us-east-1`.
  `agents.md` §11.1 требует хранения персональных данных казахстанских
  резидентов в ДЦ на территории РК — для прототипа это допустимо, для
  платного пилота нет. `packages/pd` — единственная точка доступа к
  персональным данным (имя, email, адрес доставки) с конфигурируемым
  бэкендом (см. [ADR-0005](./docs/decisions/0005-pd-backend-abstraction.md));
  сегодня по умолчанию — та же Supabase-сессия, но вторая реализация
  (`createPostgresPdBackend`, `PD_BACKEND=postgres`) уже написана и
  покрыта тестами — механизм переключения готов, физического переноса
  данных в ДЦ на территории РК ещё не было (см.
  [runbook переезда](./docs/runbook-migration.md), раздел 4).
- **Маскирование перед LLM.** `maskPII()`/`unmaskPII()` (`packages/pd`,
  agents.md §11.2) готовы и покрыты тестами, но вызывать их пока некому:
  `FEATURE_LLM_ASSIST=false`, вызовов внешних моделей в рантайме нет
  (agents.md §2). Тип `MaskedPayload` уже существует для будущего
  intake-enhancer'а — функция, которая его вызовет, физически не сможет
  принять немаскированный текст.
- **Интейк — каталог с текстовым быстрым добавлением поверх, не
  свободный NLP-парсер целой заявки.** Основной путь — выбор позиций из
  фиксированного справочника (`apps/web/app/lib/catalog.ts`, дублирует
  `packages/db/src/seed/catalog.ts`). Поверх него `intake-actions.ts`/
  `request-actions.ts` реально вызывают `matchNomenclature`/
  `extractQuantity`/`extractDeadline`/`extractBudget` — быстрое
  добавление позиции по короткой текстовой строке («баннер 2×1м, 5 шт»)
  с подсказкой категории по накопленным алиасам консьержа. Разбор целой
  заявки одним свободным текстом (agents.md §14) — остаётся отдельной,
  не собранной задачей; каталожный выбор для основного потока даёт те
  же `request_items` в БД без риска, что парсер угадает позицию неверно.
- **Подбор поставщиков для RFQ — скоринг подключён, веса дообучаются при
  staff-инициированном закрытии заказа.** `createRfqsForOrder` использует
  `passesHardFilters`/`scoreSupplier`/`pickExplorationCandidate` из
  `packages/engine/match` (жёсткие фильтры → топ-N на позицию по скору →
  слот исследования, agents.md §8C, проверено живым Playwright e2e
  против боевой БД — `rfqs.selection_reason` несёт реальные признаки и
  баллы). Контур обучения замкнут (`apps/web/app/lib/recalibration.ts`):
  при переходе заказа в `closed` под staff-актёром признаки из
  `rfqs.selection_reason.features` и факт «попал ли поставщик в
  утверждённый план» идут в `recalibrateMatchWeights()`
  (`packages/engine/learn`, настоящий SGD), новый снапшот `'matcher'`
  пишется в `model_snapshots` (RLS `model_snapshots_insert_staff` —
  сознательно staffOnly, не по владению заказом: это общая модель, а не
  данные одного покупателя), `createRfqsForOrder` читает последний
  снапшот перед скорингом вместо жёстких `DEFAULT_WEIGHTS`. Честная
  оговорка: закрытие заказа покупателем (`BUYER_OR_STAFF` по графу
  переходов) не пишет снапшот — RLS его бы и не пустила; обучение
  смещается по времени до следующего staff-закрытия, а не теряется.
  `servesCities` всегда `null` (обслуживает любой город) — в
  `supplier_profiles` нет колонки под географию поставщика.
- **Прогноз срока — подключён к реальной надёжности поставщика.**
  `apps/web/app/lib/comparison.ts` больше не считает срок наивно
  (заявленный + буфер); при staff-закрытии после подтверждённой поставщиком
  доставки `recalibrateLeadTimeForSupplier()` пересчитывает `k'` поставщика
  по всей истории доставленных заказов
  (`packages/engine/leadtime`, тот же принцип «сдвиг к 1.0 при малой
  истории») и дописывает снапшот `'leadtime'`; экран сравнения читает
  последний снапшот и применяет `applyReliability()` — без истории
  `k'=1.0`, прогноз вырождается в прежнее поведение.
- **Document Engine.** `documents` в схеме была, но ни один путь в
  apps/web в неё не писал — `apps/web/app/lib/documents.ts` закрывает
  это: счёт на предоплату пишется при переходе в `prepaid`, акт
  выполненных работ — при `closed`, оба с реквизитами QAJET
  (`settings.qajet_requisites` — единственная строка settings, видимая
  и покупателю, RLS `settings_select_public_requisites`) и данными
  заказчика. Просмотр — `/documents/[id]`, не PDF: структурированный
  `meta` JSON, отрендеренный как страница.
- **Очередь уведомлений — dev-first.** При рассылке RFQ приложение сохраняет
  адресата, защищённую ссылку и payload в `outbox` со статусом `pending`;
  админ смотрит очередь на `/admin/outbox`. Внешний Resend-worker остаётся
  подключаемым адаптером и не нужен для локального запуска или демонстрации.
- **Автотаймер.** `time_entries` пустая — не так: `apps/web/app/lib/
  autotimer.ts` пишет реальное время при каждом staff-инициированном
  переходе стадии (время в предыдущей стадии = сейчас − последний
  `order_stage_events`), `/metrics` показывает настоящее среднее по
  заказам с записями. Честная оговорка: клиентского механизма «пауза
  после 60с бездействия» (agents.md §9) нет — таймер серверный и
  считает по фактическим переходам, не по активности вкладки браузера.
- **`/demo`.** Маршрут не существовал вообще (найдено при аудите —
  ни разу не зафиксировано ни выполненным, ни осознанно отложенным).
  Теперь есть: 8 сцен спеки, управление пробелом/стрелками, реальные
  цифры текущего демо-заказа на `quotes_received` (сцены 1/3/4/5/6) и
  агрегаты по всей демо-истории (сцены 2/8); сцена 7 (утверждение,
  аудит, документы) содержательно требует уже закрытый заказ — честно
  подписана как пример по другому заказу сида, не тому же самому.
  Каждая сцена — ссылка «Открыть на сцене →» на настоящий, уже
  собранный экран, а не переизобретённая копия вёрстки.
- **Ответ поставщика по защищённой ссылке реализован.** Консьерж видит
  на стадии `rfq_sent` индивидуальные ссылки `/rfq/respond/[token]`.
  Токен — HMAC с отдельным скоупом и TTL; БД дополнительно сверяет его с
  nonce RFQ. Ссылка позволяет без входа сделать быстрый ответ
  «берусь/не берусь», а затем отправить КП; повторная отправка блокируется
  RPC и статусом RFQ. Авторизованный путь `/supplier/rfq/[id]` сохранён.
- **Команда покупателя.** Владелец компании может пригласить менеджера на
  `/buyer/team`: Auth-приглашение и профиль `public.users` создаются одной
  owner-only server action, service-role клиент изолирован в
  `apps/web/lib/supabase/admin.ts`.
- **Аудит доставки.** Переход `shipped → delivered` доступен только
  поставщику, назначенному в утверждённом плане. Для нескольких поставщиков
  заказ остаётся `shipped`, пока каждый не подтвердит доставку; история
  переходов создаётся PostgreSQL-триггером, а не клиентской вставкой.
- **`/metrics` — временная ссылка для жюри реализована.** Кнопка на
  самом экране (видна только под сессией админа) выпускает подписанный
  токен на 24 часа (`?jury=<токен>`) — по нему экран открывается вообще
  без входа. Честно про механизм: RLS не может выразить «авторизован по
  владению секретом из URL», поэтому данные для такой ссылки читаются
  через `service_role`-клиент (`apps/web/app/metrics/_jury-access.ts`) —
  единственное осознанное исключение в apps/web из правила «никогда под
  service_role» (обоснование в комментарии там же), авторизация — сама
  проверка токена, а не RLS. Живьём проверено: без токена/с
  подделанным/просроченным токеном — редирект на `/login` как раньше;
  с валидным токеном (сгенерированным вручную) — экран доходит до чтения
  данных и падает именно на отсутствии `SUPABASE_SERVICE_ROLE_KEY` в этой
  песочнице (ключ не задан локально) — то есть цепочка авторизации
  работает верно, а сам факт получения реальных чисел по валидному
  ключу не проверен живьём в этой сессии.
- **Тест изоляции поставщиков в CI — подтверждён.** `.github/workflows/ci.yml`,
  джоба `rls-isolation`:
  `supabase/setup-cli` поднимает локальный Postgres 17 (только сервис
  `postgres`, HTTP-слой Supabase исключён — `auth.uid()`/`auth.users`
  идут из образа Postgres, а не из GoTrue), `pnpm --filter @qajet/db
  db:migrate` (новый скрипт, `drizzle-orm/postgres-js/migrator`)
  накатывает `packages/db/migrations`, затем `pnpm --filter @qajet/db
  test:rls` (сам фильтр раньше не матчил файл теста — `vitest run rls`
  против `supplier-isolation.test.ts` — тоже почитано). В этой песочнице
  разработки Docker-демон не запускается (нет systemd, `dockerd` падает
  на правах), поэтому весь путь `supabase start` → `db:migrate` →
  `test:rls` не прогнан локально целиком — только каждая часть по
  отдельности. Реальный прогон на GitHub Actions `34686363385` завершён
  успешно: миграции, 23 DB/RLS-теста и PD backend против Postgres прошли.
  Локально Docker-демон по-прежнему недоступен.
- **Production Supabase schema/data — отдельный gate.** Vercel deploy не
  накатывает SQL автоматически: применение миграций `0022`–`0025`, seed и
  проверка live Auth должны выполняться против production Supabase через
  защищённый `DATABASE_URL`/service-role workflow; таких credentials в этой
  сессии не было и они не хранятся в GitHub.
- **Self-hosted Supabase (Auth/REST) — конфиг написан, не запущен.**
  `docker-compose.supabase.yml` поднимает минимальный набор (`db` на
  образе `supabase/postgres`, `auth`/GoTrue, `rest`/PostgREST и
  маленький собственный шлюз, не Envoy апстрима — обоснование в
  [ADR-0008](./docs/decisions/0008-self-hosted-supabase-minimal-services.md))
  рядом с основным `docker-compose.yml`. `docker compose ... config`
  (мердж/синтаксис) и генератор ключей (`docker/supabase-init/generate-keys.mjs`
  — HS256 JWT, подпись независимо перепроверена) реально прогнаны в
  этой сессии; сам `docker compose ... up` и живой вход через шлюз —
  нет, тот же Docker-недоступен-в-песочнице лимит, что у `rls-isolation`
  выше. Таблица «Проверено vs не проверено» —
  [runbook переезда](./docs/runbook-migration.md).
- **Мобильная оболочка (фаза 7, вне текущего финиша).** Capacitor не собирает Next.js с Server
  Actions в статику — мобильное приложение будет webview на развёрнутый
  адрес с нативными плагинами (push, haptics, шаринг — уже вызываются из
  `apps/web/app/lib/native-bridge.ts`; камера заложена в план, но никуда
  не подключена — нет схемы хранения вложений). Регистрация push-токена
  на сервере не реализована — `apps/mobile/README.md`. Нативные проекты
  `android/`/`ios/` не сгенерированы (нужны Android Studio/Xcode, которых
  нет в песочнице разработки).
- **Desktop-автообновление.** `apps/desktop` собирается и пакуется по-настоящему
  (`.deb`/`.rpm`/`.AppImage`, проверено живой сборкой), но
  `tauri-plugin-updater` не подключён — нужен подписанный релиз-канал,
  преждевременно настраивать до первого опубликованного релиза.
- **Self-hosted Supabase (Auth/PostgREST).** `docker-compose.yml`
  поднимает свой Postgres и MinIO, но не сам Auth/REST-слой Supabase —
  `apps/web` продолжает говорить с `NEXT_PUBLIC_SUPABASE_URL` по HTTP.
  Три реальных пути указаны в
  [runbook переезда](./docs/runbook-migration.md#3-authrest--то-что-перенос-postgres-не-решает),
  ни один не реализован в этой сессии — self-host полного Supabase
  (Kong+GoTrue+PostgREST) заслуживает отдельной сессии.

## Переезд на собственные серверы

Репозиторий размещён на GitHub и развёрнут на Vercel: [production](https://qajet-seven.vercel.app/).
Приложение с первого коммита не имеет
рантайм-зависимостей от платформы (`output: 'standalone'`, ADR-0002).
`docker-compose.yml` + `apps/web/Dockerfile` — рабочий, проверенный
живьём образ и стек (Next standalone + Postgres 17 + MinIO); пошаговый
[runbook переезда](./docs/runbook-migration.md) фиксирует, что перенесено
и проверено, а что осталось организационным вопросом (Auth/REST-слой,
физический перенос персональных данных в ДЦ на территории РК).
