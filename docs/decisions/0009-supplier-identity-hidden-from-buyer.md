# ADR-0009 — Личность поставщика скрыта от покупателя; история staff — ролевая, не персональная

Дата: 2026-09-08
Статус: принято

## Контекст

Явное бизнес-требование: с точки зрения покупателя QAJET сам и есть его
поставщик — единственный закупочный партнёр. Реальные исполнители — это
поставщики QAJET, покупателю не видны ни в UI, ни в данных, которые может
прочитать его сессия. Причина: лояльность должна принадлежать QAJET, а не
конкретному исполнителю, которого можно обойти напрямую в следующий раз.
Покупатель по-прежнему видит срок по каждой позиции (это даёт исполнитель,
но не раскрывает личность) и решения по существу (что предложено, что
отбраковано и почему) — только не название компании-исполнителя, её
портфолио или контакты.

Второе, равное по важности требование: у консьержа/админа история «кто
поставлял куда» обязана сохраняться ПОЛНОСТЬЮ и не теряться при смене
персонала — состав концьержей будет меняться, кто-то придёт позже и должен
видеть историю заказов, которые вёл не он.

## Аудит перед изменениями

Общий вывод: модель "внешний отдел закупок" уже была заложена в agents.md
и в основном соблюдалась в RLS. Конкретные найденные дыры:

1. **`supplier_profiles`/`supplier_stats`** — `using: sql\`true\``, читать
   мог любой `authenticated`, включая покупателя. Единственная реальная
   утечка личности поставщика на уровне БД (не только UI).
2. **`documents`** (`documents_select_via_order`) — не фильтровал по
   `type`: покупатель мог прочитать `supplier_invoice` (внутренний
   документ на исполнителя, покупателю не адресован).
3. Три buyer-страницы напрямую называли компании-исполнители:
   `/buyer/suppliers` (витрина карточек с именами), `/buyer/messages`
   (треды подписаны именем поставщика), мастер заявки (`requests/new`,
   копирайтинг «видно, кому и почему выбран поставщик»).
4. **История staff уже была ролевой, не персональной** — `staffOnly`
   всюду проверяет `current_role() in ('concierge','admin')`, а не
   `concierge_user_id`/`actor_user_id` конкретной строки.
   `orders.concierge_user_id` — это write-once бирка, которую нигде не
   читают для контроля доступа (`onDelete:'set null'`). Однако при этом
   аудите вскрылся отдельный, не связанный напрямую с видимостью баг:
   **`current_role()`/`current_company_id()` не проверяли `is_active`**
   — деактивированный сотрудник (`users.is_active = false`, единственный
   физически возможный способ «убрать» концьержа: `order_stage_events.
   actor_user_id` references `users` с `onDelete:'restrict'`, жёсткое
   удаление невозможно, если человек уже что-то сделал) продолжал бы
   проходить `staffOnly` вечно.

## Решение

- `supplier_profiles_select_all`/`supplier_stats_select_all` (identity.ts):
  `using: true` → `company_id = current_company_id() or staffOnly` —
  видят сам поставщик (свой профиль/дашборд роста) и staff (подбор, экран
  сравнения консьержа). Имена policy не переименованы (оставлены
  `_select_all`), чтобы `drizzle-kit generate` не спросил интерактивно про
  rename — поведение изменено, имя нет.
- `documents_select_via_order` (procurement.ts): добавлено `and (type <>
  'supplier_invoice' or staffOnly)`.
- `current_role()`/`current_company_id()` (миграция
  `0008_deactivated_staff_lose_access.sql`, рукописный SQL — тот же
  прецедент, что `enforce_order_transition` в 0001): добавлено `AND
  is_active` в `WHERE`. Побочный эффект, тоже верный: деактивированный
  сотрудник компании-покупателя теряет доступ к данным компании так же,
  как деактивированный staff — доступ к staffOnly.
- UI: `/buyer/suppliers` → `/buyer/reorder` (карточки без названий
  компаний, повтор по истории СВОИХ заказов), `/buyer/messages` — треды
  подписаны заказом и «QAJET», не именем исполнителя, мастер заявки —
  копирайтинг переписан («QAJET запрашивает предложения», не «видно,
  кому и почему»). `loadRequestComparison()` (`apps/web/app/lib/
  comparison.ts`) помечена комментарием: содержит реальные названия
  исполнителей, вызывать только из concierge/admin-гейтед маршрутов.
- Новый RLS-регрессионный тест
  (`packages/db/src/__tests__/staff-history-survives-turnover.test.ts`):
  concierge B (не связанный с заказом) видит заказ/RFQ/order_stage_events
  concierge A; после деактивации A теряет доступ, B — нет.

## Осознанный остаточный риск (не исправлено, отложено)

`rfqs.supplier_company_id` и `plan_lines.supplier_company_id` остаются в
строках, которые видит покупатель (`rfqs_select_buyer_of_request`,
`plan_lines_select_via_plan`) — это сырой UUID, не имя. Прямого раскрытия
личности нет: `companies` не даёт покупательской сессии прочитать
supplier-строку (`companies_select_own`/`companies_select_staff` — ни та,
ни другая не открывает покупателю чужую компанию), значит UUID
поставщика для покупателя нерасшифровываем через прямой запрос к БД.
Остаточный риск — корреляционный: если у покупателя несколько заказов, он
может заметить повторяющийся UUID и сделать вывод «это тот же исполнитель,
что в прошлый раз», не зная, кто это. Закрыть полностью можно только
представлением (view) без этой колонки или column-level GRANT/REVOKE
поверх RLS — оба варианта ощутимо больше по объёму и риску регрессии, чем
сделанные точечные фиксы, а UUID сам по себе не строка идентичности.
Решение: принять как есть, документировать здесь. Если станет реальной
проблемой (например, покупатель размечает поставщиков между собой по
переданным вручную id) — заводить отдельную задачу на view-слой для
`rfqs`/`plan_lines`/`threads`, а не чинить точечно.

## Как проверено

- Три policy применены к боевой БД
  (`eoqcktgvnzayyinulbch`) через `apply_migration`,
  `get_advisors(security)` до/после — одинаковый набор предупреждений
  (только ожидаемые `SECURITY DEFINER` и отключённая проверка утечки
  паролей), новых находок нет.
- `pnpm lint && pnpm typecheck && pnpm test && pnpm --filter @qajet/web build`
  — зелёные.
- Новый RLS-тест написан по образцу `supplier-isolation.test.ts`
  (impersonation через `request.jwt.claims`, не доверие к тому, что
  приложение само не сделает запрещённый запрос); в песочнице сессии не
  запускается (нет `DATABASE_URL`), гоняется в CI (`rls-isolation` job,
  локальный Postgres из Supabase CLI, миграции применяются из
  `packages/db/migrations`).
