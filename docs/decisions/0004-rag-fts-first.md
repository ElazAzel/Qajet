# ADR-0004 — RAG фазы 0: FTS5 сейчас, векторный слой отдельным заходом

Дата: 2026-09-06 (векторный слой добавлен 2026-09-08)
Статус: принято, реализовано полностью

## Контекст

В одобренном плане реализации RAG-система описана как гибридный поиск:
FTS5 (BM25) + `sqlite-vec` по локальным эмбеддингам через
`@huggingface/transformers`, без единого внешнего API-ключа.

## Решение

В этой сборке реализована только часть FTS5. Векторный слой сознательно
отложен, а не упущен по недосмотру — по трём причинам:

1. **Вес и риск зависимости.** `@huggingface/transformers` тянет ONNX
   Runtime и модель эмбеддингов (десятки МБ, скачивается при первом
   использовании) — это заметно увеличивает поверхность отказа
   инструмента разработки в первой же фазе, когда важнее, чтобы каркас
   проекта был безусловно надёжен.
2. **`sqlite-vec` как загружаемое расширение** через `node:sqlite`
   (`allowExtension` + `loadExtension`) — рабочий путь, но непроверенный
   на этой машине на дату решения; сначала стоило убедиться, что базовый
   FTS5-индекс через `node:sqlite` (тоже experimental API Node) сам по
   себе стабилен — что и было сделано и подтверждено (`pnpm rag:sync`,
   `pnpm rag:search`, `pnpm rag:check` работают).
3. **Отдача уже есть без векторного слоя.** Ключевой BM25-поиск по
   `agents.md`, ADR и журналу — то, ради чего вообще заводится RAG на
   этом этапе («чтобы ничего не забыть») — уже полноценно работает.
   Семантический поиск добавляет recall на перефразированных запросах,
   но не является условием полезности инструмента.

## Что сделано

- `tools/rag/src/db.ts` — индекс на `node:sqlite` (встроенный, без
  нативной компиляции), таблица `documents` + внешняя FTS5-таблица
  `documents_fts` с триггерами синхронизации.
- `tools/rag/src/corpus.ts` — нарезка `agents.md` по заголовкам ## и ###,
  плюс ADR (`docs/decisions/`), журнал (`docs/journal/`) и сгенерированное
  состояние (`docs/state/`).
- `tools/rag/src/state.ts` — `docs/state/{routes,packages,ledger}.md`
  генерируются из фактической файловой системы репозитория, не пишутся
  руками. `ledger.md` — чек-лист фаз с автоматической отметкой по наличию
  файлов-свидетелей.
- CLI: `pnpm rag:sync` (перегенерировать state + переиндексировать),
  `pnpm rag:search <запрос>`, `pnpm rag:check` (индекс не отстал от кода —
  для CI), `pnpm rag:log <текст>` (запись в журнал сессии).
- MCP-сервер `tools/rag/src/mcp.ts`, подключённый в `.mcp.json` —
  инструменты `qajet_search`, `qajet_ledger`, `qajet_log` доступны прямо
  из сессии Claude Code.

## Векторный слой — реализован (2026-09-08)

Все три причины отсрочки из раздела «Решение» закрыты:

1. **Вес зависимости.** `Xenova/paraphrase-multilingual-MiniLM-L12-v2`
   в q8-квантованном виде — реально ~130 МБ (не «десятки МБ», как
   ожидалось на дату первого решения, но и не 465 МБ fp32-варианта той
   же модели). Кэшируется в `tools/rag/.cache/` (не коммитится,
   `.gitignore`), скачивается один раз при первом `pnpm rag:sync`.
   Модель — XLM-R база, покрывает русский и казахский (agents.md
   требует RU/KZ/EN).
2. **`sqlite-vec` как загружаемое расширение.** Подтверждено: грузится
   через `node:sqlite`'s `allowExtension` + `sqliteVec.load(db)`,
   `vec0`-таблица и KNN-запросы (`MATCH ... AND k = N`) работают.
   Найден и обойдён реальный баг: `node:sqlite`'s параметр-биндинг не
   принимает смешанный вызов `.run(rowid, blob)` на `vec0`-таблице —
   падает с «Only integers are allows for primary key values» что с
   `Buffer`, что с `ArrayBuffer`, в любом стиле биндинга. Обход — rowid
   (всегда наш внутренний счётчик, никогда не пользовательский ввод)
   инлайнится в текст SQL, единственный параметр-биндинг — сам BLOB.
   См. комментарий в начале `tools/rag/src/db.ts`.
3. Отдача от чистого FTS5 действительно уже была — и осталась ровно
   такой же: векторный слой не заменяет BM25, а добавляется поверх.

**Как работает:** `tools/rag/src/search.ts` — гибридный поиск, FTS5 и
`sqlite-vec` KNN запрашиваются параллельно (пул кандидатов в 4× больше
лимита с каждой стороны), результаты сливаются через Reciprocal Rank
Fusion (`1/(RRF_K + позиция)` на список, `RRF_K = 60` — стандартная
константа) — без ручного подбора весов между BM25-рангом и косинусным
расстоянием, у которых принципиально разные шкалы.

**Честно про качество.** На реальном корпусе (53 документа, честно
измерено в этой сессии): точный термин или прямой синоним из текста —
семантический слой уверенно поднимает нужный раздел в топ через RRF
(запрос «холодный старт нового поставщика без рейтинга» → раздел про
слот исследования на 2-м месте). Свободный пересказ без пересечения
словаря — семантический слой один находит релевантное дальше в
топ-20 (не в топ-5), а не рядом с точным поиском; RRF в этом случае
вытягивает пересечение с FTS5 сильнее, чем чистая векторная близость.
Ожидаемо для 384-мерной q8-модели на корпусе такого размера — не
повод откладывать: гибрид не хуже чистого FTS5 ни в одном
проверенном случае, и лучше на части перефразированных запросов.

**Изменение сигнатуры:** `searchCorpus()` стала `async` (эмбеддинг
запроса требует вызова модели) — оба вызывающих места (`cli.ts`,
`mcp.ts`) обновлены на `await`.

**Схема индекса:** `SCHEMA_VERSION` в `db.ts` поднята до `'2'` —
`rag:sync` при первом запуске после обновления сам пересоберёт индекс
целиком (не только по изменению корпуса, но и по версии схемы), включая
пересчёт эмбеддингов для всех документов.
