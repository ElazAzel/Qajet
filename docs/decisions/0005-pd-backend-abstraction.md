# ADR-0005 — `packages/pd`: единственная точка доступа к персональным данным

Дата: 2026-09-07
Статус: принято

## Контекст

agents.md §11.1 требует, чтобы персональные данные казахстанских резидентов
хранились в дата-центре на территории РК. MVP-проект Supabase размещён в
`us-east-1` — это допустимо для прототипа, но не для платного пилота.
Переезд не должен требовать переписывания кода, который читает имя,
email или адрес доставки — сегодня это разбросано по apps/web как
обычные запросы к Supabase наравне с бизнес-данными (заказами, ценами).

## Решение

- `packages/pd` — единственный пакет, через который читаются персональные
  поля: `users.fullName`/`email` (контакт сотрудника), `requests.deliveryAddress`
  (адрес получателя). Роль пользователя, названия компаний, суммы, статусы
  заказов и всё остальное — не персональные данные в смысле §11.1
  (юридическое лицо, не физическое) и продолжают читаться напрямую.
- Интерфейс `PdBackend` описывает операции (`getUserContact`,
  `getDeliveryAddress`), не то, где физически лежат данные.
  `createSupabasePdBackend(supabase)` — единственная реализация сегодня:
  та же Supabase-сессия вызывающего пользователя, те же RLS-политики, что
  и у остальных запросов — пакет не поднимает привилегии и не обходит
  изоляцию ролей.
- Переезд на казахстанский ДЦ — новая реализация `PdBackend` (например,
  отдельный Postgres в РК с репликой/переносом таблиц `users`/`requests`),
  подключаемая в `createPdClient()` одной строкой. Ни один вызывающий код
  в apps/web не меняется — он знает только интерфейс.
- `maskPII()`/`unmaskPII()` (agents.md §11.2) — там же: маскирование
  структурированных известных значений (имя, адрес — вызывающий код и так
  их знает из полей заявки) плюс регуляркой email/телефон в свободном
  тексте. Результат — `MaskedPayload`, непрозрachный branded-тип: функция
  вызова внешней модели, объявленная как принимающая только
  `MaskedPayload`, не скомпилируется при попытке передать сырую строку.
  Сегодня в проекте нет ни одного вызова внешней модели (`FEATURE_LLM_ASSIST=false`,
  §2 запрещает LLM в рантайме основного сценария) — типы готовы заранее,
  для будущего опционального enhancer'а.

## Последствия

- `apps/web/app/lib/current-user.ts` — первая и пока единственная точка
  внедрения: имя и email читаются через `createPdClient(supabase).getUserContact()`
  вместо прямого `supabase.from('users').select('full_name, email')`.
  Остальные экраны, которые показывают персональные данные напрямую
  (например, мок-данные `/buyer/settings`), останутся без изменений до тех
  пор, пока не станут реальными запросами — рефакторить нечего, пока там
  моки, а не БД.
- Задача runbook переезда на казахстанский ДЦ (фаза 8) сужается до:
  поднять `PdBackend`-реализацию поверх нового Postgres, перенести/
  реплицировать персональные таблицы, переключить `createPdClient()`.
  Остальной код (заказы, движок, дизайн-система) переезда не касается.
