# ADR-0006 — Как заказ реально меняет состояние: RLS + один граф в двух местах

Дата: 2026-09-07
Статус: принято

## Контекст

До этой сессии ни один экран приложения не менял состояние заказа в БД —
единственный существующий `'use server'` во всём apps/web относился к
логину. Экран сравнения консьержа честно показывал живой расчёт
`combine()`, но кнопка «Утвердить план» не существовала физически: заявки,
RFQ, КП, планы, заказы читались, но не писались. Чек-лист
`docs/state/ledger.md` отмечал фазы 4–5 как готовые, потому что генератор
проверяет «файл существует», а не «действие работает» — de facto
кликабельного пути от `quotes_received` до `closed` не было.

agents.md §6 требует: «Переходы состояний — единственная функция
`transition(order, to, actor)`, прямые `update state` из UI отсутствуют
физически». Нужно было решить: где физически проходит эта единственная
функция и как БД не даёт её обойти.

## Решение

- `packages/engine/src/order/transition.ts` — чистая функция
  `transition(from, to, actor)`, граф рёбер взят дословно из
  `packages/db/src/seed/generator.ts` (та же модель жизненного цикла, что
  уже сгенерировала и проверила демо-историю 24 заказов). Возвращает
  `{ok:true}` или `{ok:false, reason}` — не бросает исключение, вызывающий
  код сам решает, что делать с отказом.
- Единственная точка вызова в приложении —
  `apps/web/app/lib/actions/order-actions.ts` (`proposePlan`, `approvePlan`,
  `advanceOrderStage`). Каждая функция: резолвит актёра из сессии
  (`orderActorFor()` — owner/manager становится `buyer` или `supplier` в
  зависимости от `companies.type`, concierge/admin — `staff`), проверяет
  переход через `transition()` ДО записи, пишет через RLS-сессию текущего
  пользователя (не `service_role`), логирует `order_stage_events`.
- Вместо `service_role`-ключа (которого нет ни локально, ни гарантированно
  на Vercel) — точечные RLS-политики в
  `packages/db/src/schema/procurement.ts`: INSERT на `plans`/`plan_lines`/
  `plan_rejections`/`supplier_payouts` для staff, UPDATE на `plans`/`orders`
  для staff и отдельно для покупателя (по своей компании), INSERT на
  `order_stage_events` с проверкой `actor_user_id = auth.uid()`. Это
  идиоматичный для Supabase путь — RLS уже была источником истины для
  чтения (§3.4, тест изоляции поставщиков), запись пошла по той же модели
  вместо добавления второго, привилегированного пути.
- Второй, независимый барьер — Postgres-триггер `enforce_order_transition`
  (`BEFORE UPDATE` на `orders`), проверяющий пары `(from_state, to_state)`
  по тому же графу, что и `transition.ts`. Если кто-то обратится к таблице
  напрямую в обход `order-actions.ts` (баг, будущий рефакторинг, ручной
  SQL) — Postgres откажет в переходе, которого нет в графе, а не тихо
  запишет мусор.

## Почему не `service_role`/RPC

Единственная функция per spec — не обязательно единственная функция в
смысле «одна хранимая процедура в Postgres». Настоящая логика выбора
плана (`combine()`) — TypeScript, не SQL: `proposePlan()` физически не
может быть чистой Postgres-функцией, она должна прочитать КП, посчитать
комбинаторику и только потом писать. Поэтому «единственная функция» здесь
— единственный модуль в apps/web, через который проходят ВСЕ записи
состояния, а не единственная хранимая процедура. RLS + триггер — это
ограничение по периметру («что вообще разрешено записать»), а не замена
бизнес-логики.

## Последствия

- Граф переходов существует в двух местах: `packages/engine/src/order/
  transition.ts` (TS, актёры, источник истины) и SQL-функция
  `enforce_order_transition` в миграции `0001_pale_lockjaw.sql` (только
  пары состояний, без актёров). Расхождение возможно, если один
  поправить и забыть про другой — риск задокументирован явно, единого
  генератора для обоих пока нет.
- RLS-политики достаточно широкие внутри роли: любой staff (concierge/
  admin) может обновить `orders`/`plans` ЛЮБОГО заказа (не только своего),
  любой buyer — только заказы своей компании, но без проверки, что именно
  ОН, а не другой сотрудник той же компании, должен был утвердить этот
  конкретный план. Для прототипа это приемлемо (то же самое верно и для
  чтения — `users_select_same_company`), для платного пилота потребует
  более тонких политик или колоночных грантов.
- Реально работает сейчас: весь цикл от `draft → estimated → prepaid →
  rfq_sent → quotes_received → plan_proposed → plan_approved →
  suppliers_paid → in_production → shipped → delivered → accepted →
  closed` (с сверкой refund/surcharge/exact), плюс `on_hold`/`cancelled`/
  `disputed` как рёбра графа (без выделенного UI под них). Интейк новой
  заявки, отправка RFQ и приём КП от поставщика по форме подключены к
  записи следующей сессией (см. `docs/journal/2026-09-08.md`) — сквозной
  цикл проходим с нуля от текстовой заявки, проверено Playwright-сценарием.
  Добавление write-политик для этого куска цикла на несколько часов внесло
  два дефекта RLS (бесконечную рекурсию `requests`↔`rfqs` и утечку изоляции
  поставщиков) — см. ADR-0007 про сам дефект и приём, которым он найден.
