# Проверка истории миграций перед объединением веток

Этот шаг проверяет только историю миграций. Он не применяет SQL, не подключается
к базе и не подтверждает готовность релиза, резервной копии или RLS.

## Почему недостаточно сравнить номера файлов

Drizzle 0.45.2 берёт наибольший `created_at` из
`drizzle.__drizzle_migrations` и применяет только миграции, у которых `when`
в `meta/_journal.json` больше этого значения. Имя файла не определяет порядок
применения. Хэш — SHA-256 полного UTF-8 текста SQL, включая комментарии и пробелы.
Сам migrator не проверяет совпадение исторических хэшей.

Поэтому нельзя исправлять конфликт простым переименованием файлов, менять SQL
уже применённых миграций или перезаписывать журнал/ledger другой веткой.

## Offline-проверка

Получите актуальный полный экспорт только служебного журнала через разрешённое
подключение к нужной базе. Не нужны ключи, пароли, бизнес-таблицы или персональные
данные. Пример read-only запроса для оператора с доступом:

```sql
SELECT coalesce(json_agg(row_to_json(m) ORDER BY m.created_at, m.id), '[]'::json)
FROM (SELECT id, hash, created_at FROM drizzle.__drizzle_migrations) AS m;
```

Сохраните JSON-массив в локальный файл вне репозитория. Отдельно зафиксируйте,
какой среде принадлежит экспорт и время получения. Отсутствующая таблица не
равнозначна подтверждённому пустому ledger: выясните, как до этого применяли SQL.
Ручные изменения и миграции, применённые другим инструментом, этим журналом
не покрываются. Для них отдельно сравните фактические функции, политики и схему.
Входные JSON/SQL должны быть обычными файлами не более 8 MiB каждый, а не symlink.
Исходные SQL и journal должны разрешаться внутри выбранного каталога миграций;
ledger, наоборот, хранится отдельно и передаётся явным путём. Это не SQL-анализатор.

```sh
node tools/ops/check-migration-lineage.mjs packages/db/migrations /path/to/ledger.json
node --test tools/ops/check-migration-lineage.test.mjs
```

Коды завершения:

- `0`: исходники согласуются только с предоставленным снимком ledger.
  Список `pending` при этом может быть непустым: новые миграции ещё не применены.
- `1`: повреждённый ввод, несовпадение хэша, неизвестная применённая миграция,
  пропуск старой неприменённой миграции или некорректный исходный журнал.
- `2`: исходники прочитаны, но ledger не предоставлен. Проверка базы НЕ выполнена.

Даже при коде `0` отчёт сохраняет `productionVerified: false` и
`releaseReadiness: "NOT_CHECKED"`. Скрипт не проверяет подлинность, полноту
экспорта, текущую схему, среду, работу SQL, данные или возможность отката.
Не используйте синтетический ledger, собранный из исходников, как свидетельство
применения миграций. Проверка запускается явно; конфигурация CI не меняется.

Проверенные исходники:

- PR23: `632be18feae7898eed8c229db506c609cba32931`.
- SQL-хэши и журнал `0000–0058` совпадают.
- main `0059–0062`: timestamps `1794119412174`, `1794119412175`,
  `1794119412176`, `1794320000000`.
- PR23 `0059–0062`: timestamps `1793939040000`, `1793948952134`,
  `1793949940666`, `1793951640243`.

Если база уже прошла main `0059`, все четыре старых entry PR23 будут пропущены
по времени. Это условный вывод по алгоритму, не доказательство состояния production.
Если в базе уже была другая ветка, сначала нужна отдельная сверка её истории.

### План объединения

1. **Снять фактическое состояние.** Проверить свежие SHA обеих веток, полный
   служебный ledger, фактические функции/политики и воспроизводимость резервной
   копии. До этого не менять журнал, snapshots и production.
2. **Сохранить main.** Не заменять main целиком содержимым PR23: в main уже есть новая
   форма заявок, продолжение после входа и изменение комиссии. Не импортировать
   старые snapshots PR23, в которых сохраняется default 23%.
3. **Не дублировать готовое.** Функция quote revision в двух `0059` идентична;
   main `0060` уже содержит эквивалентную защиту owner invite. Наличие в Git
   не означает применения в базе. Тест `quote-revision-guard.test.mjs` из PR23
   надо привязать к canonical main `0059_quote_revision_authorization.sql`,
   а не возвращать старое имя ради теста.
4. **Переносить независимые исправления отдельно.** Проверка Auth redirect,
   строгая сводка gates, обработка ошибок проверки backup и изолированные
   onboarding-тесты не требуют нового SQL. Они всё равно требуют тестов на
   новом main. Изменения jobs включают обе route, `job-response`, dispatchers,
   `learning/query` и `recalibration`; workflow проверяется отдельно, без
   запуска production jobs и без автоматического повтора batch.
5. **План покупателя переносить согласованно.** После проверки ledger подготовить
   forward-миграцию для безопасного `get_buyer_plans`. Сначала сделать RPC
   доступным, затем перевести все readers: `buyer-case`, `buyer-order`,
   `order-confirmation` и закрытие заказа в `order-actions`. После проверки
   клиентов закрыть прямой buyer SELECT из `plans` и согласованно обновить
   `approve_plan`/`request_plan_change`, права и schema cache. Не откатывать
   защиту возвращением широкого buyer SELECT. Проверить изменение возвращаемого
   типа RPC и зависимости в тестовой полной Supabase до production.
6. **Политики документов оставить отдельным блоком.** В main уже закрыт supplier
   доступ, но PR23 добавляет owner/manager, активную buyer-компанию и явный
   список типов. Это отдельная forward-миграция после разрешённой проверки;
   её тесты в рамках этой сверки не запускались.
7. **Выделить новую историю только после сверки.** Следующие свободные номера и
   timestamps назначаются с учётом актуального main и ledger. Не объединять
   вслепую новые комиссионные исправления с конфиденциальностью планов.
   Snapshots должны соответствовать итоговой схеме, включая default 15%.
8. **Релизный барьер.** Проверить clean install и обновление с фактически
   применённой линии в полной Supabase, разрешённые RLS/RPC и пользовательские
   сценарии, backup/restore, затем build/typecheck/lint и проверки exact SHA.
   Preview Ready или успешный Vercel status не подтверждают эти пункты.

### Границы текущего результата

Этот патч добавляет только offline checker, синтетические Node-тесты и инструкцию.
Миграции, комиссионные файлы, CI, production и состояние PR23 не меняются.
Production ledger, фактическая схема и релизные проверки остаются непроверенными.
