# Резервное копирование и восстановление: что проверено, что нет

Статус на 2026-09-20: **процедура логического восстановления отрепетирована
локально и найдены три места, где простое восстановление даёт неработающую или
менее защищённую систему.** Production **не** проверялся: восстановление из
резервной копии Supabase Cloud, RPO, RTO и ответственный оператор —
`EXTERNAL BLOCKER`. Бэкап, который никогда не восстанавливали, не проверен; здесь
восстанавливали копию локальной базы, а не production.

Не запускайте это против production и не восстанавливайте поверх работающей базы.

## Что делалось

Логический дамп (`pg_dump -Fc`) локального стека → новый изолированный контейнер
из того же образа Supabase Postgres (`17.6.1.167`) → сверка → полный набор
`pnpm --filter @qajet/db test:rls` на восстановленной копии. Набор — это проверка
не «строки на месте», а «система действует»: RLS, права, целостность.

## Что нужно, чтобы восстановленная копия работала

Простое «залить дамп схемы `public`» даёт 77 упавших тестов из 166. Нужны пять
шагов в таком порядке; при них проходят все 166.

1. **Новый экземпляр Postgres того же мажорного образа**, с ролями Supabase
   (`anon`, `authenticated`, `service_role`).
2. **Бизнес-данные и журнал миграций**: `pg_dump -n public -n drizzle`,
   `pg_restore --no-owner --clean --if-exists`.
3. **Auth и метаданные Storage целиком**, а не только данные, и **от служебной
   роли** `supabase_admin`: `pg_dump -n auth -n storage`. От обычной роли
   `postgres` восстановление упирается в права на схемы (`permission denied for
   schema auth`, 366 ошибок). Заливка одних данных `auth.users` в пустой образ
   не работает вовсе: в нём нет колонок, которые создаёт GoTrue.
4. **Определение `auth.uid()` той версии, которую использует приложение.** См.
   находку 1.
5. **Глобальные привилегии по умолчанию.** См. находку 2.

В ручной репетиции остались 4 ошибки `pg_restore --clean` про зависимости
от схемы `auth`, которые тогда сочли безвредными. Автоматический `--verify`
теперь не допускает исключений для таких ошибок: ненулевой статус любого
восстановления означает `FAIL`. Ошибки надо устранить на отдельной тестовой
копии, а не игнорировать по совпадению трёх счётчиков.

## Три находки репетиции

### 1. Версия схемы Auth определяет, работает ли RLS

В голом образе `auth.uid()` читает только `request.jwt.claim.sub`; в базе,
которую мигрировал GoTrue, — ещё и JSON `request.jwt.claims`. Приложение и все
тесты передают JWT вторым способом. После простого восстановления `auth.uid()`
возвращал NULL, и всё закрывалось: «Только активный покупатель может создать
заявку». Это отказ в безопасную сторону, но система не работает.

Правило восстановления: **схему Auth должна привести в порядок та же версия
GoTrue, что работает в бою** (её собственные миграции), либо восстановить схему
`auth` целиком с сохранением функций. Проверка одной командой после восстановления:

```sql
select prosrc from pg_proc where oid = 'auth.uid()'::regprocedure;
```

В теле должен быть `request.jwt.claims`.

### 2. Дамп схемы теряет глобальные привилегии по умолчанию (безопасность)

Миграция 0043 отзывает `EXECUTE` у `PUBLIC` для новых функций:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE postgres REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;
```

Это глобальная настройка, в схему `public` она не входит, и `pg_dump -n public`
её не переносит. В восстановленной копии её не было, и тест
`новая функция не получает EXECUTE для anon автоматически` **упал**: любая функция,
созданная после восстановления, стала бы доступна анонимной роли. Без этого теста
потеря осталась бы незамеченной.

Шаг 5 процедуры выполняет эту команду заново. После восстановления сверьте:

```sql
select pg_get_userbyid(defaclrole), defaclnamespace::regnamespace, defaclobjtype, defaclacl
from pg_default_acl;   -- должна быть строка postgres / (глобально) / f
```

### 3. Файлы Storage не входят в дамп базы

В дамп попадают строки `storage.objects` (метаданные), но не сами файлы: они
лежат в хранилище Storage. Восстановленная база без файлов даёт вложения, которые
скачать нельзя. На момент репетиции локальный Storage был пуст (после очистки
тестовых данных), поэтому **восстановление файлов не проверялось (`NOT RUN`)**.

## Что измерено, и чему это не равно

| Величина | Значение | Что это значит |
| --- | --- | --- |
| Размер базы | 20 МБ | демо-данные, не пилот |
| Новый экземпляр | 5–16 с | зависит от кеша образа |
| Восстановление шагов 2–5 | 4 с | |
| Итого для этой базы | ~9 с | **это не RTO production**: другой размер, другая платформа, нет Auth-службы и Storage |
| Набор проверок на копии | ~20 с | |

**RPO и RTO для production не измерены.** Для Supabase Cloud их определяет тариф
(ежедневные копии или восстановление на момент времени) и то, как быстро человек
успеет начать; проверить это можно только репетицией на реальном проекте.

## Чего нет, и что нужно решить владельцу

- **Ответственный оператор не назначен.** Кто и по чьей команде восстанавливает.
- **Тариф и резервные копии Supabase Cloud** для проекта `qajet` не проверялись:
  какие копии есть, на какой срок, доступно ли восстановление на момент времени.
- **Восстановление файлов Storage** и **проверка версии GoTrue** — обязательные
  пункты будущей репетиции на реальном (но не production) проекте.
- **Данные в Сингапуре** (ADR-0011): любая копия, снятая с production, содержит
  персональные данные и должна храниться по тем же правилам, что и они.

## Как повторить репетицию

Из корня репозитория, с работающим локальным Supabase, в Git Bash (для путей
внутри контейнеров нужен `MSYS_NO_PATHCONV=1`):

```bash
export MSYS_NO_PATHCONV=1
S=supabase_db_Qajet; D=qajet_restore_rehearsal
IMG=$(docker inspect $S --format '{{.Config.Image}}')
docker run -d --name $D -e POSTGRES_PASSWORD=postgres -p 54399:5432 "$IMG"
# дождаться: docker exec $D pg_isready -U postgres -h 127.0.0.1
docker exec $S pg_dump -U postgres -d postgres -Fc -n public -n drizzle \
  | docker exec -i $D pg_restore -U postgres -d postgres --no-owner --clean --if-exists
docker exec $S pg_dump -U supabase_admin -d postgres -Fc -n auth -n storage \
  | docker exec -i $D pg_restore -U supabase_admin -d postgres --clean --if-exists
docker exec $S psql -U postgres -d postgres -At -c "select pg_get_functiondef('auth.uid()'::regprocedure)" \
  | docker exec -i $D psql -U supabase_admin -d postgres -q -v ON_ERROR_STOP=1
docker exec $D psql -U postgres -d postgres -c \
  "ALTER DEFAULT PRIVILEGES FOR ROLE postgres REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC"
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54399/postgres \
  pnpm --filter @qajet/db test:rls
docker rm -f $D
```

Не запускайте набор на копии повторно без пересоздания: после двух прогонов в копии
оказалось 24 строки пользователей против 9 в источнике, то есть часть тестов пишет
вне откатываемых транзакций, и повторный прогон давал «duplicate key».

## Снятие копии: `tools/ops/backup-database.mjs`

Репетиция выше выполнялась вручную. Скрипт автоматизирует снятие копии и
ограниченную проверку читаемости, а не все шаги полного восстановления:

```bash
node tools/ops/backup-database.mjs --url="postgresql://…" --verify --keep=14
```

Скрипт снимает две части (`public`+`drizzle` и `auth`+`storage` от
`supabase_admin`), рядом сохраняет определение `auth.uid()` и предупреждает,
если оно старой версии (находка 1). `--verify` поднимает одноразовый контейнер
того же образа, восстанавливает туда копию и сверяет число строк с источником.
Оба `pg_restore` выполняются с `--exit-on-error`; оба запроса `psql` — с `-X`
и `ON_ERROR_STOP=1`. Ненулевой/отсутствующий статус, сигнал или ошибка запуска
любой из этих команд немедленно дают `FAIL` без сообщения «ПРОВЕРЕНО».
Пустой или некорректный вывод и расхождение счётчиков тоже дают `FAIL`.
В `finally` выполняется попытка удалить одноразовый контейнер, в том числе после
ошибки проверки; результат удаления эта узкая правка не проверяет.

Совпадение трёх счётчиков не доказывает равенство строк или целостность всех
таблиц. Источник читается после дампа и может измениться между запросами;
расхождение требует разбора или новой репетиции, а не снятия проверки ошибок.
Две части дампа также не используют общий snapshot.

`pg_dump` берётся из запущенного контейнера `supabase_db_*`, чтобы его версия
совпадала с сервером; отдельная установка PostgreSQL на хост не нужна.

Исторический прогон 2026-09-20 против локального стека: дампы 0.5 МБ и 0.3 МБ,
восстановление прошло, заказы/пользователи/компании — 43/7/18 и в источнике,
и в копии. Эта запись не подтверждает успешные статусы `pg_restore` и `psql`:
в прежнем скрипте они не проверялись. Для исправленного скрипта нужен новый
прогон на отдельном локальном Supabase. **Против production скрипт не запускался.**

Регрессии запускаются без Docker, сети и данных БД:
`node --test tools/ops/backup-database.test.mjs`. Тесты исполняют CLI во временном
каталоге, перехватывая все внешние команды. Они проверяют fail-closed поведение,
а не реальную восстановимость архива. Входят в корневой `pnpm test` до Turbo.

Чего скрипт не делает: не выгружает файлы Storage (в дампе только метаданные),
не применяет отдельно сохранённое `auth.uid()` и глобальные default privileges,
не проверяет RLS и права на копии (это полный набор `test:rls` по процедуре
выше) и не решает, где копии хранятся. Копия с production содержит
персональные данные — к ней применимы те же правила хранения (ADR-0011).
