# Код обращения (supportId): от жалобы до регрессионного теста

Вместо распределённого трейсинга. Для текущего трафика достаточно одной
JSON-строки на сбой и кода, который пользователь может назвать.

## Что видит пользователь

Если действие упало непредвиденно, пользователь читает текст и
«Код обращения: 061C58CF» — 8 символов, заглавные hex.

**Не всякий отказ получает код.** Это важно при разборе:

| Что произошло | Что видит человек | Код обращения |
| --- | --- | --- |
| Бизнес-отказ: `RAISE EXCEPTION` в функции БД (SQLSTATE `P0001`, иногда `23514` из `RAISE`) | Авторский текст отказа, например «Нужна причина от 5 до 2000 символов» | **Нет** |
| Нет прав (`42501`) | «Недостаточно прав для этого действия.» | Да |
| Конфликт: `23505`, `40001`, `55P03` | «Эти данные уже изменились. Обновите страницу…» | Да |
| Запись не найдена (`PGRST116`) | «Запись не найдена или недоступна.» | Да |
| Всё остальное | «Не удалось выполнить действие.» | Да |

Следствие: жалоба на понятный текст без кода — это бизнес-отказ, его ищут по
самому тексту в миграциях (`grep` по `RAISE EXCEPTION`), а не в журнале. И
наоборот, служебная фраза вроде «Покупатель не может менять внутренние поля
заказа», показанная человеку, — сигнал, что путь неправильно заведён: так и было
с выбором варианта плана (миграция 0051).

## Где искать

1. Vercel → проект `qajet` → *Logs* (Runtime Logs), окружение Production.
2. Фильтр по тексту: сам код, например `061C58CF`.
3. Найдётся одна строка вида:

```json
{"level":"error","event":"action_failure","at":"2026-09-20T05:43:07.817Z",
 "supportId":"061C58CF","operation":"order.approvePlan","code":"conflict",
 "errorName":"PostgrestError","sqlstate":"40001"}
```

Поля закрыты типом (`apps/web/app/lib/server-log.ts`): в строке нет текста
исходной ошибки, SQL, email, тел заявок и токенов. Исходный текст пишется только
при `NODE_ENV=development`.

## Как разобрать строку

- **`operation`** — `<модуль>.<действие>`. Это имя действия сервера в
  `apps/web/app/lib/actions/`: `order.approvePlan` — `approvePlan` в
  `order-actions.ts`. Примеры: `order.advanceOrderStage`, `order.selectPlan`,
  `supplier.confirmSupplierDelivery`, `attachment.upload`, `company.createCompanyWithOwner`,
  `message.sendMessage`. Задачи по расписанию пишут `job.outbox` и `job.learning`.
  Полный список: `grep -rhoE "(actionFailure|failureText|authErrorText)\('[a-zA-Z]+\.[a-zA-Z]+'" apps/web/app`.
- **`code`** — класс из таблицы выше (`forbidden`, `conflict`, `not_found`,
  `internal`, …).
- **`sqlstate`** — код Postgres/PostgREST, если он есть. `42501` — политика RLS
  или грант; `23505` — уникальность (двойной клик, повтор); `40001` — сериализация;
  `PGRST116` — ожидалась ровно одна строка.
- **`errorName`** — тип исключения, помогает отличить сбой БД от сбоя сети.

## Что в журнале нет, и это честное ограничение

В строке **нет** пользователя, компании, заказа и заявки — только время `at`,
операция и код. По одному коду нельзя узнать, чей это заказ. Поэтому у автора
жалобы спрашивают: **что он нажимал, на каком экране и во сколько**. По
`operation` и времени этого хватает для воспроизведения; если нужны данные
заказа — спросите номер закупки у самого пользователя.

Не добавляйте идентификаторы в строку журнала ради удобства без решения:
правило проекта — только разрешённые непрозрачные ID, операция, безопасный код,
длительность и ограниченные счётчики (`AGENTS.md`, «Data and observability»).

Второе ограничение — срок хранения журналов на текущем тарифе Vercel. Он
короткий; проверьте фактический срок в настройках проекта, а не по памяти. Если
жалоба приходит позже срока, код потерян. **Именно это, а не желание красивого
графика, оправдало бы таблицу обращений и экран `/admin/support`.** До появления
реального случая потери кода не строим.

## От кода к исправлению

1. Найти строку по коду, записать `operation`, `code`, `sqlstate`, время.
2. Открыть действие сервера, найти вызываемую RPC или запрос.
3. Воспроизвести локально на своей базе (`supabase start`, `pnpm dev:local-env`),
   никогда не на production и не с реальными данными пользователя.
4. Написать **падающий** тест: для БД — в `packages/db/src/__tests__/` на реальном
   PostgreSQL, для логики приложения — рядом с кодом. Убедиться, что он красный по
   той причине, которую нашли.
5. Минимальное исправление, тест зелёный, затем широкий набор
   (`pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm --filter @qajet/db test:rls`).
6. Записать находку и её статус в `docs/release/readiness.json`, если она
   касается готовности.

## Когда вернуться к трейсингу

Только если реальные инциденты пилота покажут, что кода обращения не хватает: не
удаётся связать сбой с шагом, действие делает несколько вызовов и неясно, какой
упал, или нужна длительность по шагам. До этого OpenTelemetry, Tempo и Jaeger
не нужны.
