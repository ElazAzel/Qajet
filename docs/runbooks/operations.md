# Операционный runbook

## Быстрая проверка

1. Откройте `/api/health`: это проверка процесса и текущего commit SHA.
2. Откройте `/api/ready`: он проверяет env и запрос к `settings`; HTTP 503
   означает, что выпуск не готов принимать рабочие действия.
3. Войдите админом и проверьте `/admin/outbox`, `/admin/learning` и
   `/admin/finance`.
4. Для локального запуска используйте `pnpm dev:bootstrap`. Скрипт поднимает
   только локальный Supabase, применяет миграции и пересоздаёт demo-данные.
   Его нельзя запускать с production `DATABASE_URL`.

## Письмо не ушло

- Найдите запись в `/admin/outbox` по получателю и типу события.
- `failed` можно повторить кнопкой Retry после устранения причины.
- При отсутствии `RESEND_API_KEY` это ожидаемая dev-деградация: передайте
  сообщение оператору или подключите Resend в environment, не подставляя ключ
  в код и не меняя payload вручную.
- Убедитесь, что cron защищён `CRON_SECRET`; в production запрос без него
  должен получить 401.
- В Vercel Hobby частые cron-запуски недоступны, поэтому `vercel.json` не
  регистрирует worker автоматически. Для production подключите внешний
  scheduler или `pg_cron`, вызывающий `/api/jobs/outbox` и `/api/jobs/learning`
  с `Authorization: Bearer $CRON_SECRET`; до этого очередь обслуживается
  оператором из `/admin/outbox`.

## Оплата, возврат и доплата

- Оператор подтверждает входящий банковский перевод в UI; сумма хранится в
  `payment_facts`, а не выводится из стадии заказа.
- Повтор с тем же idempotency key безопасен только для той же операции и суммы;
  другой amount/kind должен быть отклонён.
- При закрытии система вычисляет settlement по подтверждённым входящим и
  исходящим фактам. Не исправляйте `orders.state` или суммы прямым SQL.

## Спор или несоответствие поставки

Зафиксируйте проблему в треде заказа, переведите заказ в предусмотренное
состояние и сохраните документ/фото в private storage. Поставщик не должен
получать внутренний тред или данные другого поставщика. После решения создайте
новую версию плана; утверждённый план не редактируется задним числом.

## База или файлы недоступны

1. Остановите ручные повторы actions, чтобы не создавать новые банковские
   операции.
2. Проверьте `/api/ready`, Supabase status и задержку outbox/learning.
3. Снимите время и commit SHA инцидента. Восстановление делайте только в
   отдельной среде из проверенной копии; сначала сверяйте миграции и версии.
4. После восстановления выполните negative RLS checks, контрольный заказ и
   проверку скачивания private attachment.

## Откат

Откатывайте приложение на предыдущий проверенный SHA без удаления миграций и
бизнес-данных. Миграцию назад вручную не придумывайте: сначала определите,
совместима ли предыдущая версия приложения с текущей схемой. Для разрушительной
операции нужен отдельный согласованный план и backup.
