# Операционный runbook

Повседневная эксплуатация. Разовую настройку production-окружения (какие
переменные задать, где взять значение, как проверить результат) см. в
[production-environment.md](./production-environment.md).

Инструкции сверены с кодом `d2e79f2`. Это описание контракта, не подтверждение
настройки или работы production. Исторические результаты других SHA не
заменяют проверку выбранной среды.

## Быстрая проверка

1. Откройте `/api/health`: это проверка процесса и текущего commit SHA.
2. Откройте `/api/ready`: он требует восемь непустых переменных окружения,
   успешное чтение `settings`, `environment_kind = clients` и валидные
   `qajet_requisites`. Различайте `dependency: env`, `client_configuration`
   и `supabase` при 503. Список переменных и границы проверки приведены в
   [production-environment.md](./production-environment.md#runtime-readiness-contract).
   HTTP 200 не проверяет доставку почты, Vault, запуск cron или весь релиз.
   Для приёмки сверяйте также SHA из ответа с выпускаемым SHA.
3. Войдите админом и проверьте `/admin/outbox`, `/admin/learning` и
   `/admin/finance`.
4. Для локального запуска используйте `pnpm dev:bootstrap`. Скрипт поднимает
   только локальный Supabase, применяет миграции и пересоздаёт demo-данные.
   Его нельзя запускать с production `DATABASE_URL`.

## Письмо не ушло

- Найдите запись в `/admin/outbox` по получателю и типу события.
- Кнопка Retry для admin возвращает только `failed`-строку в `pending`.
  Она не отправляет письмо сама и не заменяет настроенный worker. Перед
  повтором проверьте причину отказа и возможное принятие письма провайдером;
  не создавайте копию записи и не меняйте payload вручную.
- Текущий адаптер при `NODE_ENV=production` и отсутствующем или пробельном
  `RESEND_API_KEY` отказывает **до claim очереди**. Авторизованный вызов outbox
  возвращает 503, строки и число попыток остаются без изменений. Это поведение кода; наличие
  этого SHA в выбранном деплое проверяется отдельно.
- Только вне production отсутствие ключа включает `local-sink`: внешний
  отправитель не вызывается, хотя обработка может отметить строку как `sent`.
  При непустом ключе Resend используется и вне production, поэтому тестовая
  среда с ключом тоже способна отправить настоящее письмо.
- `RESEND_API_KEY` и `RESEND_FROM_EMAIL` обязательны для client readiness и
  strict release gate. Fallback sender в низкоуровневом адаптере не является
  разрешением выпускать пилот без явно настроенного отправителя.
- `sent` и заполненные timestamps outbox не подтверждают доставку получателю.
  Нужен отдельный сценарий с синтетическим сообщением и контролируемым
  адресатом. HTTP-успех Resend с message ID подтверждает принятие провайдером.

## Фоновые jobs и ручная проверка

- Миграция `0057` регистрирует `qajet-drain-queues` в `pg_cron` с расписанием
  `*/15 * * * *`. Факт применения миграции и активности задания в конкретной
  среде проверяется отдельно; второго расписания в GitHub нет.
- Функция читает Vault `qajet_cron_secret` и `qajet_app_url`. Если любое
  значение отсутствует или пусто, она тихо выходит без HTTP-запросов.
  `/api/ready` это состояние Vault не проверяет.
- При наличии конфигурации `pg_net` ставит два POST-запроса, outbox и learning,
  без предварительного `/api/ready` и без анализа их результатов. Успешная
  строка `cron.job_run_details` означает успех SQL-вызова, не обработки очереди.
- `.github/workflows/jobs.yml` имеет только ручной `workflow_dispatch`.
  Для него нужны repository secret `CRON_SECRET` и проверенный `APP_URL`;
  отсутствие переменной URL включает зашитый адрес, поэтому перед запуском
  убедитесь, что целью служит согласованная среда. Runtime `CRON_SECRET`
  должен совпадать с Vault и, если используется ручной путь, с GitHub secret.
- Запрос к jobs без точного `Authorization: Bearer …` получает 401;
  отсутствие runtime-секрета закрывает доступ в любом окружении.
- Ручной workflow сначала проверяет readiness. При не-200 это `NOT RUN` с
  ненулевым итогом, без вызова jobs. Иначе оба job вызываются по одному разу,
  даже при отказе первого. Для успеха нужны HTTP 200, JSON `ok: true`,
  числовой `failed: 0` и, когда присутствует, `retryUnconfirmed: 0`.
- Один вызов обрабатывает ограниченный batch: до 20 outbox-строк или до 10
  learning events. Пустой успешный batch не доказывает обработку сообщения.
  `ok: false` при HTTP 200 означает отказ элементов или неподтверждённый retry;
  детали возвращаются безопасными кодами и `supportId`.
- Автоповтор HTTP не добавлен. При 503 или timeout часть работы уже могла
  зафиксироваться. Повторы learning не атомарны, а принятие письма провайдером
  может предшествовать ошибке completion. Не считайте каждый reported failure
  подтверждением запланированного повтора. Production-alerting этим кодом не
  настроен; см. [порядок проверки](./production-environment.md#verification--in-this-order).

## Оплата, возврат и доплата

- Оператор подтверждает входящий банковский перевод в UI; сумма хранится в
  `payment_facts`, а не выводится из стадии заказа.
- Повтор с тем же idempotency key безопасен только для той же операции и суммы;
  другой amount/kind должен быть отклонён.
- При закрытии система вычисляет settlement по подтверждённым входящим и
  исходящим фактам. Не исправляйте `orders.state` или суммы прямым SQL.

## Спор или несоответствие поставки

Зафиксируйте проблему в треде заказа, переведите заказ в предусмотренное
состояние и сохраните документ/фото в private storage. Поставщик не должен
получать внутренний тред или данные другого поставщика. После решения создайте
новую версию плана; утверждённый план не редактируется задним числом.

## База или файлы недоступны

1. Остановите ручные повторы actions, чтобы не создавать новые банковские
   операции.
2. Проверьте `/api/ready`, Supabase status и задержку outbox/learning.
3. Снимите время и commit SHA инцидента. Восстановление делайте только в
   отдельной среде из проверенной копии; сначала сверяйте миграции и версии.
4. После восстановления выполните negative RLS checks, контрольный заказ и
   проверку скачивания private attachment.

## Откат

Откатывайте приложение на предыдущий проверенный SHA без удаления миграций и
бизнес-данных. Миграцию назад вручную не придумывайте: сначала определите,
совместима ли предыдущая версия приложения с текущей схемой. Для разрушительной
операции нужен отдельный согласованный план и backup.
