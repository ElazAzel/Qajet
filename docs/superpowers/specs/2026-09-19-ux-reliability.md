# QAJET: упрощение пути пользователя, подтверждённая безопасность, честные документы

## Контекст

Репозиторий заявляет `technically-ready-for-pilot`, все 9 фаз в `docs/state/ledger.md`
отмечены готовыми. Живая проверка через коннекторы Vercel и Supabase плюс аудит кода
показали, что это округление в большую сторону:

- продакшен работает на старом коммите, `/api/ready` отдаёт 503, рассылка RFQ в проде
  физически не работает;
- покупатель теряет свою заявку сразу после отправки — маршрута на `requestId` не существует;
- обязательный инвариант §3.4 «поставщик не видит данные другого поставщика» нарушен
  на вложениях;
- «зелёный CI» частично декоративен: сквозные тесты пропускаются и при этом отмечаются
  успешными.

Задача — не добавить платформе функций, а сделать существующие работающими для человека:
заявка не исчезает, статусы понятны, ошибки читаемы, дубли невозможны. Параллельно закрыть
подтверждённые дефекты доступа и привести документы и CI к реальности.

Решения пользователя, зафиксированные до начала работ:
- **Observability — минимум.** `ActionResult` с безопасным кодом и `supportId` + серверный
  структурированный лог. Без OpenTelemetry, Collector, Tempo и `/admin/traces`.
- **Тестовая БД — локальный Docker.** Боевой Supabase `qajet` не трогаем ни на запись, ни
  миграциями.
- **Объём** — правда в документах, безопасность, путь покупателя, QA, CI-ворота.

Работаем в уже созданном worktree
`C:/Users/elaza/.codex/worktrees/ux-reliability-otel/QAJET`, ветка
`refactor/ux-reliability-otel` на `22a5a88`. Ветку стоит переименовать в
`refactor/ux-reliability`: OTel из объёма выпал. Порядок — risk-first, мелкими коммитами,
для каждого подтверждённого дефекта сначала падающий тест.

## Этап 2. Путь покупателя

**2.1 Один URL на всю жизнь закупки.** Канонический адрес — `/buyer/requests/[id]`, ключ
`requestId`; старые `/buyer/orders/[id]` и подмаршруты отдают постоянный редирект. Намеренно
не вводим слово «procurement»: §4 фиксирует словарь, где заявка — это `request`. Производная
серверная модель, новой таблицы нет:

```ts
type BuyerCase = {
  requestId: string;
  orderId: string | null;
  title: string;
  stage: BuyerStage;
  nextAction: { label: string; href: string } | null;
  waitingOn: 'qajet' | 'buyer' | 'buyer_owner' | 'supplier';
  expectedAt: string | null;
  updatedAt: string;
};
```

RLS не мешает: `requests_select_own_company` (`0000:594`) уже разрешает покупателю читать
заявки своей компании.

**2.2 Семь понятных стадий вместо семнадцати.** Внутренние состояния не трогаем:

| Стадия | Внутренние состояния | Мяч у |
| --- | --- | --- |
| Получено | `draft` | QAJET |
| Нужно ваше решение | `estimated`, `plan_proposed`, `awaiting_internal_approval` | покупатель |
| Подбираем поставщиков | `prepaid`, `rfq_sent`, `quotes_received` | QAJET |
| Исполняем | `plan_approved`, `suppliers_paid`, `in_production`, `shipped` | QAJET |
| Нужна приёмка | `delivered` | покупатель |
| Завершено | `accepted`, `closed` | — |
| Проблема | `on_hold`, `disputed`, `cancelled` | QAJET |

Конкретика уходит в `nextAction`: на `estimated` — «Оплатить счёт», на `plan_proposed` —
«Выбрать вариант». Вторую параллельную таблицу `EVENT_LABEL` (`buyer/page.tsx:10-28`) убрать:
сегодня она называет то же состояние иначе, чем штамп.

**2.3 Заявка видна сразу.** После отправки — переход на `/buyer/requests/[id]`, а не
success-панель на месте. Заявка без заказа попадает в список на `/buyer` и в счётчики.

**2.4 Форма начинается пустой.** Убрать предзаполненную `CATALOG[0]`. Явный выбор «вставить
текст» или «добавить вручную»; результат разбора заменяет пустой список, а не дописывается
к фиктивной строке.

**2.5 Заявка создаётся ровно один раз.** `createRequest` принимает UUID `submissionKey`,
генерируемый при монтировании формы; уникальность `(created_by, submission_key)` в БД;
повторный вызов возвращает уже созданную заявку. Переиспользовать существующий RPC
`create_request_with_items` (`0026:392-453`) и сложившийся паттерн ключа идемпотентности из
`payment_facts` / `outbox`.

**2.6 Ошибки рядом с полем.** `fieldErrors` из `ActionResult` этапа 1, `aria-invalid`,

**2.7 Навигация.** 7 пунктов у покупателя уже уезжают в горизонтальный скролл на мобильных

  вообще, каждый прогон навсегда оставляет заявку, заказ, КП и платёжные факты.

- Сценарии: покупатель (создание → повторная отправка → кейс виден → лимит согласования →
  приёмка), поставщик (RFQ → КП → только назначенные заказы → доставка), консьерж

## Что сознательно не делаем

- Не деплоим, не мержим, не меняем переменные в Vercel и ничего не пишем в боевой Supabase.
  Недостающие `SUPABASE_SERVICE_ROLE_KEY` и `CRON_SECRET` фиксируются как внешний блокер с
  инструкцией, а не выставляются молча.
- Не вводим OpenTelemetry, Tempo и `/admin/traces`.
- Не трогаем путь поставщика, консьержа и админа сверх перечисленных дефектов доступа.
- Не решаем резидентность данных в КЗ и не включаем защиту от утечки паролей в Supabase —
  это изменения боевой инфраструктуры, идут в рекомендации.
