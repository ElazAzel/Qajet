# QAJET — полностью рабочий веб-сервис: план трёх следующих фаз

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Новая B2B-компания подключается к QAJET, проводит закупку от заявки до оплаченной и принятой поставки с документами и сверкой, затем повторяет заказ; команда обслуживает этот цикл через интерфейс, без исправления записей SQL вручную.

**Architecture:** Развивать существующие Next.js, Supabase/RLS и TypeScript-движок. Авторитетные расчёты, версии обязательств и финансовые факты согласованы между движком, транзакциями БД и UI; внешняя доставка уведомлений и обучение выполняются повторяемыми фоновыми заданиями. Local/demo, staging и production имеют отдельные данные и назначение.

**Tech Stack:** Существующие pnpm workspaces/Turborepo, Next.js 16.3.4, TypeScript strict, Drizzle/PostgreSQL 17, Supabase Auth/Storage, Vitest, Playwright, Serwist, Vercel/standalone. Версии зафиксированы репозиторием.

**Spec:** `agents.md`, особенно §3, §6–11, §13–15; ADR-0006 и ADR-0009. Предыдущий план — `docs/superpowers/plans/2026-09-12-qajet-finish.md`.

**Дата и статус:** исследование 12 сентября, план завершён 13 сентября 2026. План составлен по коду `e35dff13e226996c5021ed6db94ead97e4eadcdf`. Это новый цикл из трёх фаз; старая нумерация 0–8 остаётся историей создания модулей. Задачи ниже ещё не выполнены этим документом.

## Общие ограничения

- QAJET — продавец/подрядчик перед клиентом; поступления от покупателя и выплаты исполнителям — разные обязательства.
- Только B2B, мерч/корпоративные наборы/полиграфия; серверный запрет регулируемых категорий.
- Оплата — банковский перевод на счёт QAJET с подтверждением сотрудником; эквайринг, QR, наличные и клиентские кошельки не входят в этот план.
- База комиссии — товары/услуги без доставки; по умолчанию 23% на позицию, правка 21–24% до согласования. Применять существующие settings и границы `packages/engine/src/commission`.
- Покупателю доступны итог исполнения, доставка и раскрываемое дополнительное вознаграждение, если оно есть; личность исполнителей, их закупочные цены и комиссия QAJET не выдаются ни HTML/RSC, ни API. Staff видит полное объяснение.
- `FEATURE_LLM_ASSIST=false`; основной сценарий и алгоритмы работают без внешних моделей.
- Хранение ПД в РК — требование самого проекта из §11.1. Соответствие конкретной инфраструктуры подтверждается отдельно; переключатель `PD_BACKEND` сам по себе его не доказывает.
- Существующие опубликованные миграции не редактировать. Новые миграции нумеровать после фактического последнего номера на момент реализации и согласовывать с `_journal.json`/snapshot.
- iOS/Android исключены решением владельца. Цель этого цикла — веб-сервис и мобильный веб на 375px; нативные оболочки не являются критерием запуска.
- Секреты хранятся в окружении. Реальные покупательские данные и демо-аккаунты не смешиваются. Сброс и seed production запрещены штатным сценарием запуска.

### Конкретные разрывы, на которых основан план

1. `tools/rag/src/state.ts` и `docs/state/ledger.md` отмечают фазу по существованию хотя бы одного пути. Все галочки не означают исполнение §15. Старый finish-план, наоборот, сохранил незакрытые checkbox даже у уже написанного кода. Нужна отдельная матрица проверенных возможностей.
2. `apps/web/app/lib/actions/order-actions.ts:589–615` берёт `p50 * 0.5`, одновременно создаёт счёт и ставит `paid`. §8B требует выставлять счёт на P80. В `order-confirmation.ts` зашиты те же 50%; отдельного решения, заменяющего §8B, не найдено.
3. В `order-actions.ts:418–447` итог = цена плана + введённая пользователем поправка. Поступившие деньги не участвуют в расчёте. `CloseOrderForm` предлагает покупателю самому выбрать возврат/доплату; SQL проверяет внутреннюю согласованность этих чисел, но не сверку с оплатой.
4. Численный прогон `combine()` на 10 шт. × 1 000 ₸, setup 2 000 ₸, доставке 5 000 ₸, комиссии 23% дал: `totalSupplierKzt=12000`, сумму `lineTotalKzt=10000`, комиссию итога `2760`, сумму комиссий строк `2300`, итог `19760`. `prepareSupplierPayouts()` берёт именно строки. Значит, setup теряется в расчётной базе выплаты; последующая правка комиссии может изменить итоговую комиссию несогласованно. Проверен расчёт и прослежен код, реальная выплата не выполнялась.
5. `combine.ts:237` суммирует setup каждой строки, тогда как §8D говорит об однократной подготовке на поставщика. Требуется единая явная модель распределения этих затрат, а не отдельная поправка UI.
6. `e2e/fixtures.ts:112–114` заполняет только цену и срок: setup/minQty останутся `field_flags`, и план будет отвергнут. `order-lifecycle.spec.ts:68–74` ищет кнопку «Утвердить план», но карточка содержит ссылку «Перейти к подтверждению», а следующий экран — «Подтверждаю заказ на этих условиях». Это обнаруженные по исходникам несовместимости теста и UI; live-прогон ещё не выполнен.
7. `team-actions.ts` отправляет Auth invite, но маршрутов с `verifyOtp`/`exchangeCodeForSession`, установки/восстановления пароля в приложении не найдено. Верификация на `/admin` — таблица без управляющих действий.
8. `change_requests` существует в схеме/сиде; рабочего action/UI нет. `propose_order_plan` разрешён только из `quotes_received`. Защита неизменяемости старого плана не заменяет процесс создания и принятия новой версии.
9. `approvePlan(orderId)` не принимает ожидаемые план/версию/состав условий. Текст «подтверждаю версию N» не связан параметром с фактическим утверждением; нужна защита от изменения условий между чтением и кликом.
10. Чтение `threads` и отправка в готовые треды есть, но создание тредов в application write-path и миграциях не найдено. Поля attachments и Docker MinIO сами по себе не дают рабочую загрузку файлов.
11. `autotimer.ts:58` пишет `Date.now() - stageStart`, включая ночь и ожидание. `metrics.ts:62` считает конверсией любой неотменённый order, хотя order создаётся ещё при intake; `metrics.ts:89` считает повтором даже `estimated`.
12. `recalibration.ts` перечитывает `price_observations`, но application-запись новых цен не найдена. Запуск только от staff закрытия; очередь/cron отсутствуют. Прогноз срока использует общий интервал RFQ→доставка заказа, а не начало исполнения и индивидуальную доставку поставщика.
13. `packages/pd` используется для текущего пользователя; адрес в `order-confirmation.ts` и профили в других loaders/actions читаются/пишутся напрямую. `PD_BACKEND=postgres` не переносит Auth email, сообщения, документы и все остальные копии ПД.
14. `.env.example` содержит пустые локальные ключи; `db:reset` требует заранее настроенные сервисы и удаляет данные таблиц целиком. Защита только по `NODE_ENV` не доказывает, что указана локальная/demo БД.

### Как это соотносится с прежним планом

Старый finish-план в основном закрывал отдельные дефекты: standalone, PII-токены, логистику, аудит/доставку поставщиком, RFQ-ссылки, приглашения и отчётность CI. Эти реализации сохраняются. Незавершённые пользовательские цепочки переносятся в задачи 1.1–1.4 и 2.1–2.6 ниже. Новые найденные расхождения денежных расчётов, согласования версий, общения, активного времени и обучения добавляются как обязательная часть завершения сервиса. README с утверждением об «одних внешних gates» требует пересмотра по итогам реализации.

## Проверка изменений при реализации

Для каждой задачи: сначала зафиксировать конкретный воспроизводимый сценарий, внести локальное изменение с нужными SQL/UI проверками, выполнить соответствующий тест, проверить diff и сделать небольшой commit. При документационных изменениях достаточно проверки документа/ссылок; тесты приложения из-за одного текста не дублировать.

```powershell
# Обязательная проверка кода перед выпуском:
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm test
corepack pnpm --filter @qajet/web build

# Только против настроенной изолированной БД/staging:
corepack pnpm --filter @qajet/db db:migrate
corepack pnpm --filter @qajet/db test:rls
corepack pnpm --filter @qajet/pd test:rls
corepack pnpm --filter @qajet/web e2e

corepack pnpm rag:sync
corepack pnpm rag:check
git diff --check
```

Наличие всех секретов, отсутствие skip в обязательной выборке и совпадение SHA проверяет release gate из 1.1/3.3. Ни один command с exit 0 при полностью пропущенном наборе не является доказательством. Новые task-specific spec-файлы запускаются по точному имени через `vitest run`/`playwright test` после их создания; в финальный обязательный набор входят все перечисленные сценарии.

Оценку календарных сроков следует давать после 1.1: неизвестное состояние production-схемы и первый настоящий HTTP lifecycle могут выявить дополнительные дефекты. Фазы завершаются по доказательствам выше, а не по истечении условного количества дней.
