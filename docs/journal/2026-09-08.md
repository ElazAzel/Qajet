- **~01:10** Полный `pnpm lint && pnpm typecheck && pnpm test && pnpm build`
  зелёный. Начал живую E2E-проверку Playwright-скриптом (не в CI, разовый
  скрипт в scratchpad) против `pnpm dev`: покупатель создаёт заявку →
  логин концьержа не мог продвинуться дальше `/buyer` — после логина
  любая следующая навигация (даже reload той же `/buyer`) откатывала
  сессию на `/login`. Не флуктуация окружения (проверил: proxy-статус
  чистый, Supabase Auth отвечает 200 стабильно при прямом curl-опросе) —
  добавил временный `console.error` в `requireCurrentUser()` и увидел
  настоящую причину: `ERROR 42P17: infinite recursion detected in policy
  for relation "requests"` при джойне `users → companies` (ровно тот
  запрос, что `current-user.ts` делает на каждом заходе). Причина —
  `requests_select_supplier_via_rfq` (эта сессия, ниже) и уже
  существовавшая `rfqs_select_buyer_of_request` (миграция 0000) стали
  подзапрашивать друг друга. Разорвал цикл `SECURITY DEFINER`-функциями
  `rfq_request_ids_for_current_supplier()` /
  `buyer_company_ids_for_current_supplier()` (тот же приём, что уже был
  применён для `current_company_id()`/`current_role()` при аналогичной
  рекурсии на `users` в прошлой сессии) — миграция
  `0003_slim_morg.sql` / `fix_requests_rfqs_rls_recursion`.

- **~01:45** С починенной рекурсией E2E-скрипт пошёл дальше: заявка →
  оценка → предоплата → RFQ разошёлся. На дашборде демо-поставщика
  (`supplier@demo.qajet.kz`, компания «Uka Print») — 0 RFQ, хотя заявка
  требовала `merch`/`screen-print`, которые формально покрываются сидом.
  Причина — данные, не код: у «Uka Print» не было строки в
  `supplier_profiles` вообще (пустой профиль, компания как будто есть, но
  ничего не покрывает) — честный пробел демо-данных, а не баг RFQ-dispatch.
  Добавил профиль (`merch`/`screen-print`,`embroidery`,`dtf-print`) прямым
  UPDATE — этой компанией никто раньше не пользовался (0 RFQ/КП/payouts
  на неё до этого момента), безопасно.

- **~02:10** С профилем поставщик стал получать RFQ — и дашборд показал
  ЯВНО больше строк, чем реально отправлено этой компании (18 вместо 3 по
  прямому SQL-подсчёту). Это не дубликаты в БД — это утечка изоляции:
  `rfqs_select_buyer_of_request` полагалась на «кому видна заявка, тому
  видно и RFQ», а видимость заявки только что расширилась на поставщика
  (`requests_select_supplier_via_rfq`) — поставщик A стал видеть ВСЕ RFQ
  той же заявки, не только свою. Тот же анти-паттерн нашёлся ещё в 7
  местах: `request_items_select_via_request`, `estimates_select_via_request`,
  `prepayments_select_via_request`, `plans_select_via_request`,
  `plan_rejections_select_via_request`, `orders_select_via_request`,
  `quotes_select_buyer_of_request`, `quote_lines_select_buyer_of_request`
  — все писаны как «id in (select id from requests)» без `where`, то есть
  «требования: requests видна только покупателю» было НЕЯВНЫМ. Переписал
  все на явную проверку `buyer_company_id = current_company_id()` (+
  staffOnly), кроме `request_items` (обоснованно нужен и поставщику — без
  позиций нечего оценивать в форме ответа). Полный разбор и приём —
  ADR-0007. Миграция `0004_abandoned_raider.sql` /
  `fix_supplier_isolation_leak_via_requests`.

- **~02:30** Проверка фикса: поведенчески (18→3 строки RFQ на дашборде
  поставщика — совпало с прямым SQL-подсчётом) и точечно для
  `quote_lines` — тот самый обязательный тест §15
  (`packages/db/src/__tests__/supplier-isolation.test.ts`) не

  одноразовые фикстуры (два поставщика, одна заявка, по одному КП

  поставщика B. Фикстуры удалены после проверки. `get_advisors` (security)
