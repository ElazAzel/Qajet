# Рост сети и подбор поставщиков: позиция и план

Статус: **предложение** (2026-09-23). Ничего здесь не принято владельцем. Уровни
доказательств — как в `agents.md`: `CONFIRMED` — видно в коде или данных,
`ASSUMPTION` — гипотеза, которую надо проверить на пилоте.

## 0. Главный вывод

1. Подбор поставщиков уже **детерминированный и типизированный** почти во всём
   (`packages/engine/src/match/match.ts`, `CONFIRMED`): жёсткие фильтры с
   перечислимой причиной отказа, семь признаков 0..1, взвешенная сумма, веса
   дообучаются по исходам заказов, у каждого включения есть `selection_reason`.
   Переписывать его не нужно. Нужно закрыть три дыры, описанные ниже.
2. Узкое место старта не алгоритм, а **то, что поставщик не смотрит на сайт**.
   Первым делом нужен канал «достучаться», а не новая модель.
3. «Собрать как можно больше клиентов и поставщиков» — **неверная цель для
   этапа**. Для управляемого реселлера поставщик без заказов уходит через месяц, а
   клиент без быстрого исполнения не возвращается. Цель — плотность в 2–3
   категориях одного города, где на каждый RFQ приходят 3+ допустимых КП.

## 2. Три дыры в подборе

### 2.1. «Всегда одни и те же» — петля обратной связи

`winRate` и `freshnessScore` растут у того, кто уже выигрывает, а приглашение даёт
шанс выиграть снова. Слот исследования разрывает петлю только для новичков
(история < 3): поставщик с 5 заказами год назад застревает посередине навсегда.
Штраф `currentLoad` считает открытые заказы, а не долю приглашений. Это `CONFIRMED`
по коду; насколько это сильно на реальных данных — `ASSUMPTION`, данных пилота нет.

Предложение, по порядку:

1. **Сначала измерить.** Метрика «покрытие сети»: доля верифицированных
   поставщиков категории, получивших ≥1 RFQ за 30 дней, и доля RFQ у топ-3.
   Показать на `/admin/learning`. Без неё любое «справедливое» правило — вкусовщина.
2. **Потолок экспозиции** — детерминированная пере-сортировка после скоринга:
   поставщик, получивший больше `max_share` приглашений категории за 30 дней,
   опускается ниже следующего, если разница в балле меньше порога. Качество не
   приносится в жертву: сильный отрыв по баллу всё ещё выигрывает.
3. **Расширить пул исследования**: не «история < 3», а «давно не приглашали» тоже.
4. **Сделать розыгрыш воспроизводимым**: сейчас Thompson sampling берёт
   `Math.random`. Сид от `order_id` даст тот же выбор при повторе — это и есть
   «детерминированный» ответ, который можно объяснить задним числом.

### 2.2. Профиль поставщика: дешевле, быстрее, качественнее, премиальнее, своя доставка

Сейчас в профиле есть категории, техпроцессы, города, минимальный заказ и срок по
умолчанию (`supplier_profiles`). Нет сравнения между поставщиками. Предлагаемый
**типизированный профиль**, вычисляемый, а не заполняемый вручную:

| Ось | Источник | Значения |
| --- | --- | --- |
| Цена | КП поставщика / медиана категории (`price_observations`, `quote_lines`) | `budget` · `market` · `premium` |
| Скорость | обещанный срок против фактического (`leadtime`), медиана ответа на RFQ | `fast` · `normal` · `slow` |
| Надёжность | вовремя, без споров, оценка покупателя (уже в `supplier_stats`) | три числа + N, без сводного балла (§8F) |
| Своя доставка | тег в `capabilities` (`own_delivery`), подтверждается консьержем | да / нет |

Правила: ось показывается только при `N ≥ 3` наблюдений, иначе «мало данных»;
«премиальный» — не оценка качества, а ценовой сегмент, и в интерфейсе они
разведены. Профиль видят консьерж и админ; покупатель видит только то, что уже
разрешено ADR-0009 (личность поставщика скрыта).

Это же даёт консьержу быстрый ответ на запрос клиента «надо дешевле» или «надо к
пятнице»: фильтр по оси вместо перебора.

### 2.3. Обучение на дополнительных данных — и польза самому QAJET

Сигналы, которые уже пишутся, но не используются для подбора (`CONFIRMED` по
схеме): цены проигравших КП, выбор покупателя между тремя вариантами плана
(дешевле / с запасом по сроку / рекомендованный), причины отказа поставщика,
время консьержа по стадиям.

Что из них извлечь, по ценности для бизнеса:

1. **Минуты консьержа на заказ по категориям и поставщикам** — главный показатель
   продукта. Поставщик, с которым уходит вдвое больше минут на уточнения, дорог,
   даже если дёшев в КП. Это признак для матчера и аргумент для инвестора.
2. **Предпочтение покупателя** (цена против срока) — чтобы «рекомендованный» план
   попадал в выбор чаще.
3. **Сезонность спроса** (Новый год, 8 марта, Наурыз, конец квартала) — чтобы
   заранее бронировать мощности у поставщиков, а не искать их в декабре.
4. **Точность калькулятора** (MAPE уже на `/metrics`) — меньше разница между
   предоплатой и итогом, меньше возвратов и доплат.

Чего не делать: LLM в контуре выбора поставщика. Выбор должен объясняться
признаками и воспроизводиться; LLM уместен на разборе заявки (§8A), не здесь.

## 3. Взаимодействие поставщика и консьержа

Четыре режима, от простого к сложному:

| Режим | Как | Когда |
| --- | --- | --- |
| **Приглашение (push)** | матчер выбирает, поставщику уходит RFQ и подписанная ссылка | есть сейчас |
| **Эскалация** | RFQ без ответа за 24 ч до срока (или 48 ч без срока) → строка «Поставщик молчит» в «Исключениях» консьержа → звонок | **добавлено в этой ветке** |
| **Уведомление в Telegram** | бот пишет поставщику о новом RFQ со ссылкой; эскалация идёт сначала в бота, потом консьержу | нужны решения владельца (ниже) |
| **Витрина лотов (pull)** | верифицированный поставщик категории видит обезличенные открытые лоты и сам отмечает «берусь» → консьерж приглашает | после пилота |

### Telegram: что нужно решить до кода

- **Канал.** Производственники и печатники в Алматы массово сидят и в WhatsApp, и в
  Telegram; какой канал они реально читают по работе — `ASSUMPTION`. Проверка
  стоит одного вопроса первым 10 поставщикам. Telegram Bot API бесплатен и
  привязывается ссылкой `t.me/<бот>?start=<подписанный токен>`; WhatsApp Business
  API требует верификации Meta и платных шаблонов.
- **Персональные данные.** `chat_id` и номер — персональные данные. ADR-0011 о
  резидентности в Казахстане не принят; хранить их в Singapore-проекте Supabase
  до решения — тот же риск, что и остальные ПД.
- **Секреты.** Токен бота и секрет webhook — в Vercel, владельцем.

Техническая схема, когда решения приняты: колонка привязки канала у пользователя
поставщика (миграция), маршрут webhook с проверкой секрета, канал `telegram` в
существующем `outbox` (тот же диспетчер, те же повторы и тот же отказ без ключа),
тест RLS на то, что `chat_id` не читается другими компаниями.

### Витрина лотов: почему не сейчас

Наивная витрина нарушает инвариант «поставщик A не видит данных поставщика B» и
раскрывает заявку клиента всем поставщикам категории, а не только приглашённым.
Лот можно показать только как обезличенную спецификацию без имени клиента и без
цен конкурентов. Главное —
при 5–20 заказах в месяц витрина пустая, и пустой экран учит поставщика не
заходить. Эскалация и Telegram решают ту же задачу при малом объёме.

## 4. Бизнес глазами каждого участника

**Клиент (HR, маркетинг).** Нужны скорость, одна закрывающая документация (счёт,
акт, ЭСФ) и отсутствие хлопот. Платит за то, что не надо самому обзванивать пять
типографий. Риск: первый сорванный срок = потерянный клиент. Отсюда — запас по
сроку в плане и эскалация молчащих поставщиков.

**Поставщик.** Нужны предсказуемые заказы, быстрая оплата, отсутствие гонки цен
вниз. Боится платформ, которые давят маржу. QAJET платит ему как заказчик — это
сильный аргумент, его стоит говорить прямо. Риск: мало заказов → перестаёт
отвечать. Отсюда — плотность в категории важнее ширины сети.

**Консьерж.** Нужна одна очередь «что сделать сейчас». Каждая новая фича без
очереди действий добавляет ему минут, а минуты — это и есть юнит-экономика.

**Основатель.** Нужен доказанный повторный заказ, а не функциональность. Главная
метрика пилота уже записана в спецификации (§9): доля компаний с повторным
оплаченным и принятым заказом.

**Венчурный инвестор.** Смотрит на:
- *маржу и её устойчивость* — QAJET реселлер с комиссией в заданных границах, то
  есть валовая маржа видна по каждому заказу;
- *тренд минут консьержа на заказ* — если он не падает, это агентство услуг с
  низким мультипликатором, а не продукт;
- *повторность* — B2B-закупка мерча сезонная и повторяемая по природе;
- *данные* — цены и сроки по категориям Казахстана, которых нет ни у кого, — это
  единственный потенциальный ров; сеть поставщиков сама по себе рвом не является.

Главные риски для инвестора: сервисный бизнес под видом платформы; малый средний
чек; оборотный капитал (снимается предоплатой P80, `CONFIRMED` в процессе);
сезонность; зависимость от одного консьержа.

## 5. План, по порядку

1. **Пилот** (внешнее): реальный клиент, 3–5 поставщиков в одной категории, почта
   с ключом Resend. Без этого всё ниже — оптимизация без данных.
2. **Метрика покрытия сети** на `/admin/learning` (2.1, шаг 1).
3. **Сид Thompson sampling от `order_id`** — маленькая правка движка, делает выбор
   воспроизводимым.
4. **Опрос первых поставщиков о канале** → Telegram-бот, если подтвердится.
5. **Типизированный профиль поставщика** (2.2) — когда у поставщиков будет ≥3
   наблюдений.
6. **Потолок экспозиции** (2.1, шаг 2) — когда метрика покрытия покажет перекос.
7. **Витрина лотов** — после пилота и только при объёме, при котором она не пустая.

## 6. Чего сейчас не делать

- Не расширять сеть поставщиков раньше спроса: неактивные поставщики портят
  метрику ответа и тратят минуты консьержа на верификацию.
- Не заменять матчер нейросетью: данных на порядки меньше, чем нужно, и выбор
  перестанет объясняться.
- Не строить витрину лотов до пилота.
- Не хранить Telegram/телефоны поставщиков до решения по резидентности ПД.
