## Обязательные расхождения перед продолжением

1. **Baseline устарел.** §1.2 исходного плана описывает `3274f79`, комиссию 23% (21–24%) и последнюю миграцию 0058. Проверенный main — `703300d`, journal до 0062. Сначала выполнить T01, не выбирать номер миграции по исходному плану.
2. **Экономика меняется явно.** План предлагает 25% (15–35%), minimum income 40 000 ₸ и версионирование. Main содержит 15% (10–15%). Сохранение плана не меняет работающие тарифы. В T03 оформить явный переход с фактического legacy-состояния, не переписывать утверждённые планы и не подменять новую policy простой заменой констант.
3. **В текущем SQL есть несогласованный диапазон.** [Миграция 0062](https://github.com/ElazAzel/Qajet/blob/703300dffc23e0f1adbde18aff8706c03966fb8d/packages/db/migrations/0062_qajet_commission_15.sql) меняет commission guard/RPC на 10–15%, а [guard_plan_line_contract из 0039](https://github.com/ElazAzel/Qajet/blob/703300dffc23e0f1adbde18aff8706c03966fb8d/packages/db/migrations/0039_abandoned_randall_flagg.sql) содержит 21–24%. `CONFIRMED` по исходникам; исполнения в этой сессии не было. PR #25 содержит отдельный кандидат исправления. Не выпускать только приложение на непроверенную БД.
4. **T02 ещё не закрыта в main.** [Schema main](https://github.com/ElazAzel/Qajet/blob/703300dffc23e0f1adbde18aff8706c03966fb8d/packages/db/src/schema/procurement.ts) содержит `plans_select_via_request` через `visibleToBuyerOrStaff` у таблицы с внутренними суммами. Нужны прямой PostgreSQL-тест и согласованный перенос safe DTO, readers и RPC из PR #23 на новый main. Исторические локальные тесты PR не равны проверке итоговой объединённой линии.
5. **Миграции main и PR #23 имеют расходящиеся истории.** Нельзя заменять main старым journal/snapshots PR или просто переименовать SQL. Сначала актуальный служебный ledger, фактические функции/политики и проверка истории по [runbook PR #26](https://github.com/ElazAzel/Qajet/blob/c493d6a1ff5c090fdfabda343bb228c3b4067a3a/docs/runbooks/migration-lineage.md). Применённые SQL не менять; новые номера и timestamps выбирать после сверки.
6. **Внешние гейты остаются отдельными.** Полный контур ПД Казахстана, права на каталоги, договоры партнёров, учётная модель и реальная экономика перечислены в §16.1 плана. Их проверка — `NOT RUN`; когда подтверждено, что условие требуется для реального запуска и закрывается вне репозитория, фиксировать `EXTERNAL BLOCKER`. До применимых подтверждений использовать синтетические данные.

## Как записывать результат

Для каждого изменения оставлять короткую запись:

- Дата, Txx, исполнитель, ветка, исходный и проверенный SHA.
- Что именно изменено; ссылка на commit/PR и затронутые инварианты.
- Команда или сценарий, среда, результат, ссылка на доказательства.
- Что остаётся, точная причина препятствия и следующий шаг.

Использовать значения из `agents.md`: `PASS`, `FAIL`, `NOT RUN`, `CONFIRMED`, `REPRODUCED`, `NOT REPRODUCED`, `EXTERNAL BLOCKER`, `ASSUMPTION`. `PASS` относится только к названной реально выполненной проверке на точном SHA. Исходники дают `CONFIRMED`, а не runtime PASS. Чекбокс задачи закрывается только когда все её обязательные проверки и критерии выполнены; release gates фиксируются отдельно.

Не хранить здесь секреты, DATABASE_URL, токены, приглашения, реальные адреса получателей или выгрузки бизнес-данных. Служебный ledger для сверки хранить вне репозитория.
